# /tabular-review — табличный due diligence dataroom (RF)

1. Прочитать `~/.hermes/legal/corporate-legal/CLAUDE.md` → категории запросного
   листа, материальность, house format.
2. Подтвердить: какие документы, какие колонки, куда идёт выход.
3. Построить типизированную схему, записать `.review-schema.yaml`, показать
   пользователю, подтвердить.
4. Пробный прогон (3–5 документов). Поправить схему. Подтвердить.
5. Фан-аут — по субагенту на документ, параллельно. Каждая ячейка: значение +
   состояние + дословная цитата + локация.
6. Нормализация. Флаг аутлаеров и несоответствий.
7. Выход: `.xlsx` или CSV + `_sources.csv` + markdown всегда. Work-product header.
8. Summary: объём верификации (счётчики not_present/unclear/needs_review),
   флагнутые колонки, файлы, напоминание: ячейка = зацепка, не вывод.

```
tabular-review
tabular-review --schema .review-schema.yaml --docs ./dataroom/02-Korporativnye/
tabular-review --template ma-diligence-rf
```

**`--schema <путь>`:** использовать готовую схему (повторные прогоны,
инкрементальные добавления).

**`--template <имя>`:** шаблон из `references/`. В этой поставке —
`ma-diligence-rf`.

## Purpose

У тебя пачка документов и список вопросов, на которые нужны согласованные
ответы по каждому. Request-list датарума. Аудит договоров контрагента.
Ревизия портфеля лицензий. Выход — таблица: строки-документы, колонки-реквизиты,
каждая ячейка восстановима до точных слов источника.

Это не issue-spotting. `diligence-issue-extraction` находит 30 проблем в 2000
документах. Этот навык отвечает на одни и те же 15 вопросов про каждый из 2000.
Оба легитимны, вопросы разные.

И это не замена чтения. Каждая ячейка — **зацепка для верификации, не вывод**.
Выход устроен так, чтобы верификация была быстрой, а не чтобы её пропустить.

## Колонки RF по умолчанию (`--template ma-diligence-rf`)

Типовая схема для проверки target ООО/АО при buy-side РФ. Старт, не чеклист —
заверения в договоре о продаже и запросный лист определяют реальные вопросы.

```yaml
schema:
  name: "M&A Diligence RF — Project [код]"
  columns:
    - id: counterparty
      label: "Контрагент"
      type: verbatim
      prompt: "Наименование второй стороны, точно как в документе (с ОГРН/ИНН, если указаны)."
    - id: doc_type
      label: "Тип документа"
      type: classify
      options: [dogovor_postavki, dogovor_podryada, uso, litsenziya_PO, arenda,
                zaym, kredit, dogovor_ob_otchuzhdenii_doli, trudovoy_dogovor,
                dop_soglashenie, protokol_OSU, reshenie_SD, ustav, litsenziya_regulyatora,
                93_1_nk_istrebovanie, akt_sverki, nda, drugoe]
      prompt: "Тип документа по праву РФ."
    - id: date
      label: "Дата"
      type: date
      prompt: "Дата договора/решения. Для протокола — дата собрания."
    - id: amount
      label: "Сумма/цена"
      type: currency
      prompt: "Сумма договора (₽ или валюта). Если цена в спецификации — not_present + цитата отсылки."
    - id: term
      label: "Срок"
      type: duration
      prompt: "Срок действия и автопродление."
    - id: change_of_control
      label: "Смена контроля"
      type: classify
      options: [молчит, требуется_согласие, согласие_не_безосновательно,
                автоматическое_расторжение, только_уведомление,
                право_контрагента_расторгнуть]
      prompt: "Есть ли условие о смене контроля/корпоративном событии стороны? Что происходит?"
    - id: assignment
      label: "Уступка прав"
      type: classify
      options: [молчит, требуется_согласие, без_согласия, только_аффилиатам, запрещено]
      prompt: "Уступка прав/перевод долга (ст. 382, 391 ГК): можно ли уступить без согласия контрагента?"
    - id: exclusivity
      label: "Эксклюзивность/неконкуренция"
      type: classify
      options: [нет, эксклюзивный_поставщик, эксклюзивный_покупатель, неконкуренция,
                несолиситинг, территория, mfn]
      prompt: "Ограничивает ли договор конкуренцию или свободу заключать договоры с другими?"
    - id: liability_cap
      label: "Лимит ответственности"
      type: currency
      prompt: "Лимит или неустойка (ст. 330 ГК). Указать формулу, не только число («12 мес. платы»)."
    - id: termination
      label: "Расторжение"
      type: classify
      options: [нет, любая_сторона_без_причины, только_заказчик, только_исполнитель,
                только_существенное_нарушение, одностороннее_с_уведомлением]
      prompt: "Права на одностороннее расторжение (ст. 450.1 ГК)."
    - id: approval_status
      label: "Одобрения по 45/46/84"
      type: classify
      options: [не_требуется, требуется_не_видно_одобрения, одобрение_приложено,
                одобрение_не_найдено, вопрос_открыт]
      prompt: "Крупная сделка/сделка с заинтересованностью (ст. 46/45 ФЗ-14, ст. 79/84 ФЗ-208)? Есть ли в датаруме решение об одобрении?"
    - id: pdn_152fz
      label: "ПДн 152-ФЗ"
      type: classify
      options: [нет_пдн, поручени_есть, поручения_нет, consent_нужен, трансграничка]
      prompt: "Есть обработка ПДн? Есть ли поручение на обработку (ст. 6 152-ФЗ)?"
    - id: governing_law
      label: "Применимое право"
      type: verbatim
      prompt: "Право и суд (или третейская оговорка — цитировать)."
    - id: notes
      label: "Флаги"
      type: free
      prompt: "Только [review]-флаги и короткие пометки. Не использовать как мусоропровод."
```

**Колонки под тип сделки/юрлица:**

- **Финансовые организации (ЦБ):** согласование ЦБ на сделки с долями
  (ст. 20.1 ФЗ-208 для публичных АО), пруденциальные отчёты, требования 395-1.
- **ФНС-история:** колонка `93_1_nk`: было ли истребование документов самой
  организации (ст. 93 НК) или у контрагентов о ней (ст. 93.1 НК), за какой
  период, открыта ли проверка (ст. 89 НК) — типично для датарума sale-стороны
  `[проверять по документам, не по памяти]`.
- **Трудовые:** колонка `labor`: ключевые сотрудники, изменения при смене
  собственника (ст. 75 ТК — только для руководителя, зама, главбуха),
  неоплаченный переработки-риск `[verify по документам]`.
- **Real estate:** аренда с регистрацией (ст. 651 ГК), залог/обременение из ЕГРН.
- **Доли/акции:** колонкаы для корпоративного пакета: размер доли, есть ли
  преимущественное право (ст. 21 ФЗ-14), опционные соглашения (ст. 429.2 ГК),
  корпоративный договор (ст. 67.2 ГК).

**Быстрый первый проход (6 колонок отвечают на 80% ранних вопросов):**
counterparty, date, amount, change_of_control, assignment, approval_status.
Потом расширять.

## Три состояния «не найдено»

Пустая ячейка скрывает информацию. Явно фиксировать одно из:

| Состояние | Значение |
|---|---|
| `not_present` | Документ прочитан, положения в нём нет |
| `unclear` | Что-то есть, но классифицировать уверенно нельзя |
| `needs_review` | Нашлось, но решение за юристом |

Сделка с «молчит» по уступке и «неоднозначно» — разные вещи для deal-команды.

## Workflow

### Step 0: Что и где

1. **Документы.** Локальная папка датарума, Box, Диск, список файлов. Сколько?
   Если >200 — предупредить и предложить начать с materiality-подмножества.
2. **Схема.** Пользователь выбирает шаблон или описывает колонки словами —
   структурируем в типизированную схему.
3. **Выход.** Excel или CSV — спросить. CSV и markdown записываются всегда.
   Куда сохранить — спросить.

### Step 1: Схема + подтверждение

Для каждой колонки: стабильный `id`, человекочитаемый `label`, `type`,
`prompt` (вопрос, который читатель документа задаст), для `classify` —
`options`. Записать `.review-schema.yaml` рядом с выходом. Это переиспользуемый
артефакт — можно править и перегонять новые документы. Показать, подтвердить.

### Step 2: Пробный прогон

Не гнать 200 документов на непроверенной схеме. 3–5 документов, показать строки.
- Колонки где большинство `unclear` — переписать prompt
- `classify` не влезает в options — расширить или сменить на `free`
- `verbatim` возвращает пересказ — напомнить: дословно

Поправить, перегнать пробу, подтвердить.

### Step 3: Фан-аут

По субагенту на документ, параллельно. Каждый:
1. Читает весь документ (не RAG-чанк).
2. Для каждой колонки находит релевантное положение.
3. Возвращает `{value, state, quote, location}`.

**Правило verbatim — механическое, не пожелелательное:**

- `quote` — точная копия связного текста из источника, извлекаемая по
  указанной `location`. НЕ собирать цитату из заголовка секции + «типовой
  boilerplate, который там наверняка есть». НЕ пересказывать и звать это
  дословным. НЕ восстанавливать по памяти «как обычно пишут». НЕ сшивать
  через многоточие несвязные куски.
- `location` достаточна, чтобы нормализатор открыл документ и перечитал тот же
  фрагмент (номер пункта, заголовок, страница).
- Не смог найти/скопировать точный текст (обрезка, OCR-мусор, положение
  подразумевается но не написано) → состояние `needs_review`, value null,
  notes: `quote_unavailable: <причина>`. Ячейка «answered» без настоящей
  цитаты — недопустима.
- Кавычки не нужны: нормализатор делает спот-чек, перечитывая источник по
  локации. Расхождение → `needs_review` + `quote_mismatch` + флаг на всю
  колонку расширенного чека.

**RF-специфика цитат.** В корпоративных документах РФ реквизиты часто в
пунктах с длинной нумерацией (пп. 4.2.1 п. 4 ст. 45 ФЗ-14 → цитата из
договора). Указывать локацию до уровня пункта/подпункта, а не только страницы.

### Step 4: Нормализация

После фан-аута читать таблицу колонка за колонкой — это ловит главный failure
mode табличного ревью: одна и та же оговорка трактуется по-разному в разных
документах.

- `classify`: каждый answered в options; скопления проверять — если 180
  «требуется_согласие» и 20 «без_согласия», наверное реально; если 195/5 —
  смотреть пятерых.
- `date`/`duration`/`currency`: формат единый, выбросы (99-летний срок,
  лимит 1 ₽) — `needs_review`. Суммы в USD/EUR — цитата и дата курса, если
  в договоре.
- `verbatim` и компаньон-цитаты: спот-чек по источнику от 3–5 строк или 10%
  колонки (что больше) — посимвольно. Мismatch → даунгрейд агрессивно.
- `approval_status`: если «одобрение_приложено» — цитата должна быть из
  решения/протокола, а не из договора. Если в датаруме нет ни одного одобрения
  при «требуется» — флаг всей колонке + предложение прогнать
  `diligence-issue-extraction` по корпоративному блоку.

### Step 5: Выход

Три формата:

**Markdown** (всегда, для ревью в сессии):

```markdown
| Документ | Контрагент | Дата | Смена контроля | Уступка | Одобрение 45/46 | ⚠️ |
|---|---|---|---|---|---|---|
| Пост. услуг — ООО «Ромашка» | ООО «Ромашка» ИНН 7701... | 2023-02-01 | требуется_согласие | без_согласия | одобрение_приложено (проток. от 12.01.2023) | — |
| Поставка — АО «Василёк» | АО «Василёк» | 2021-11-15 | ⚠️ unclear | молчит | требуется_не_видно_одобрения | CoC неоднозначен §14.2 |
```

**CSV** всегда + `_sources.csv` (цитаты и локации отдельным файлом).

**Excel** (`.xlsx`): каждый дата-столбец + скрытый source-столбец с цитатой;
комментарии к ячейкам дублируют цитату; цвет по состоянию (белый, жёлтый,
серый); колонка Verified — пустая, заполняет ревьюер; лист `_schema` с
определением колонок.

Work-product header из профиля + дистрибуционная пометка:

> Ревью выведено из датарума, материалы которого могут быть конфиденциальны
> или защищены адвокатской тайной. Наследует статус источников. Распространение
> за пределы круга защиты может снять защиту. Хранить с делом, рассылать
> осознанно.

### Step 6: Summary

- Сколько документов, колонок, строк завершено
- Счётчики not_present/unclear/needs_review по колонкам — это объём верификации
- Колонки где нормализация флагнула >10% строк
- Где файлы
- Напоминание: ячейка — зацепка, не вывод. Верификация обязательна до того,
  как это войдёт в заверение, schedule или memo.

## Что дальше?

Decision tree из practice profile → `## Выходные документы`. Опции кастомизировать
под результат: (1) прогнать `diligence-issue-extraction` по найденным флагам;
(2) передать таблицу в `material-contract-schedule`; (3) эскалировать 🔴-строки
аппруверу; (4) дособрать недостающие документы из датарума; (5) другое.

## Чего этот навык не делает

- **Не заменяет чтение документов.** Указывает, куда смотреть.
- **Не ставит confidence-скоров.** 0.73 — не информация. Состояния
  unclear/needs_review и дословные цитаты — это сигнал доверия.
- **Не молча пропускает документы.** Каждый указанный документ получает строку.
  Нечитаемый — строка needs_review с пометкой.
- **Не выдаёт пересказ за цитату.** Evidence trail — вся суть.

## Связь с другими навыками

- `diligence-issue-extraction` находит проблемы; этот извлекает дата-пойнты.
  Если извлечение вскрыло проблему (CoC с конкретным триггером) — предложить
  issue-extraction по документу.
- `material-contract-schedule` строит расписку существенных договоров —
  фильтрованный вид этой таблицы.
- `ai-tool-handoff` передаёт bulk, когда корпус слишком велик. Сначала —
  здесь, потом остаток наружу.

## Injection-защита выходов

Любая ячейка, originated извне сессии (цитаты договоров, имена контрагентов,
выписки), HTML-эскейпится в dashboard-выходах (textContent, не innerHTML;
URL — только http/https/mailto). В Excel/CSV — префикс `'` для ячеек,
начинающихся с `=`, `+`, `-`, `@`, и RFC 4180-квотинг CSV. Контролируем атаку:
формула в ячейке = supply-chain attack на ревьюера.

## Output safeguards

Каждый выход — work-product header. Каждая ячейка — цитата или явное состояние.
Summary прямо говорит: верификация обязательна. Колонка Verified делает
состояние аудируемым. Инструмент не даёт «не читать»; он ускоряет чтение.
