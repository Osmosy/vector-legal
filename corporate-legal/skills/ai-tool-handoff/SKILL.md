# AI Tool Handoff — передача bulk-ревью

## Shared guardrails (канон — practice profile)

**Reviewer note / decision tree / Destination check / Provenance /
No-silent-supplement / Currency trigger / Large input** — см.
practice profile (`~/.hermes/legal/<domain>/CLAUDE.md` → `## Shared
guardrails`, `## Outputs`). Блоки канонизируются там; если текст навыка
расходится с профилем — профиль контролирует.


## Purpose

Kira/Luminance хороши в одном: читать 500 договоров и находить каждую
CoC-оговорку. Они слабее в judgment — решить, реально ли конкретная CoC
срабатывает от этой структуры сделки.

Навык передаёт bulk-экстракцию правильному инструменту и гонит QA-слой на то,
что вернулось.

**До хэндоффa:** попробовать `tabular-review` сначала. Для всего, что среда
тянет — несколько сотен документов, заданная схема колонок — нативное табличное
ревью быстрее в настройке, без по-документной оплаты, и остаётся локально.
Хэндофф — когда корпус реально больше того, что тянет среда, у команды есть
лицензия и workflow, или требуется валидированная provenance-цепочка.

## Load context

`~/.hermes/legal/corporate-legal/CLAUDE.md` → AI bulk-review:
- Инструмент (Kira / Luminance / аналог / нет)
- Для чего (какие типы оговорок)
- Trust-уровень (as-is / выборочный N% / полный пересмотр)
- Handoff-процесс (кто загружает, кто QA)

Если профиль говорит «нет инструмента» → навык no-op. Всё идёт напрямую
в diligence-issue-extraction.

## Когда передавать

Передавать при всех условиях:
- Категория >50 документов (меньше — быстрее прочитать самому)
- Экстракция по типовому классу оговорок (CoC, assignment, эксклюзивность,
  MFN, расторжение, автопродление)
- Документы достаточно однородные (все клиентские на похожей форме — не
  смесь договоров, писем и протоколов)

**Не передавать:**
- Кастомные, сильно переговорённые документы
- Side letters и дополнительные соглашения (контекстозависимы; инструменты
  пропускают взаимодействие с основным договором)
- Всё, где вопрос «что это значит для сделки», а не «есть ли оговорка»

**RF-специфика:** корпоративные и судебные документы (уставы, протоколы,
решения, судебные акты) плохо экстрактируются инструментами, обученными на
англо-американских корпусах, — ручной разбор чаще быстрее. Инструменты
хорошо работают по англоязычным договорам контрагентов (международные
поставки, лицензии).

## Хэндофф

### Шаг 1: Подготовить батч

- Определить документы батча (из инвентаря dataroom)
- Указать цели экстракции по профилю (какие оговорки)
- Отметить порог материальности, чтобы отфильтровать выход инструмента

### Шаг 2: Загрузка (или инструкция загрузчику)

По профилю — кто загружает. Если это ты — сгенерировать инструкцию загрузки.
Если другой — сгенерировать запрос:

```markdown
## [Инструмент] Load Request — [код сделки] — [категория]

**Документы:** [N] документов из [путь]
**Загрузить в:** [workspace/matter инструмента]
**Цели экстракции:**
- Смена контроля / уступка
- Эксклюзивность
- MFN
- [и т.д. по профилю]

**Фильтр выхода:** флагать только где цель присутствует — не нужно
«CoC не найдено» по каждому документу.

**Вернуть к:** [дата]
```

### Шаг 3: QA-слой

Когда инструмент вернул результаты, применить trust-уровень:

**«As-is»:** втянуть в diligence-находки напрямую. (Только если профиль
прямо это говорит — редкость.)

**«Выборочно N%»:** случайно семплировать N% флагнутых документов. Для
каждого — прочитать реальную оговорку и сверить с экстракцией. Низкая
ошибка → принять батч. Ошибки → расширить выборку.

**«Полный пересмотр флагнутых»:** инструмент сузил множество (500 → 80
с CoC). Человек читает все 80. Инструмент сэкономил чтение 420 чистых.

### Шаг 4: Judgment-слой

Инструмент нашёл оговорки. Теперь judgment:

Для каждой флагнутой CoC-оговорки: реально ли срабатывает от этой сделки?
- Продажа долей vs продажа активов vs слияние — разные триггеры
- «Смена контроля» определена как? (мажоритарная доля? контроль органа?
  что-то иное?) В RF-договорах определение вариативно — цитировать
- Есть ли изъятие для этого типа сделки?

Это часть, которую инструмент не делает. Выход идёт в diligence-находки
в house-формате.

## Выход

> QA-выжимка ниже выведена из документов dataroom, которые защищены;
> наследует их статус. Распространение за круг защиты снимает защиту.
> Хранить с делом.

```markdown
## AI Tool Handoff Summary — [категория]

**Инструмент:** [Kira / Luminance / аналог]
**Документов обработано:** [N]
**Цели экстракции:** [типы оговорок]

### QA

**Trust-уровень:** [из профиля]
**Выборка:** [N] документов проверено
**Ошибка:** [X]% — [принять / расширить выборку / полный пересмотр]

### Результаты

| Тип оговорки | Документов флагнуто | После judgment | Материальных |
|---|---|---|---|
| Смена контроля | [N] | [N — реально срабатывает от структуры сделки] | [N над порогом] |
| Уступка | [N] | [N] | [N] |

**→ [N] находок добавлено в diligence-вопросы**
**→ [N] согласий добавлено в closing-checklist**
```

## Что дальше?

Decision tree из профиля. Кастомизировать под результат.

## Чего этот навык не делает

- Не запускает Kira/Luminance — управляет хэндоффом и QA. Экстракцию
  запускает человек (или сам инструмент).
- Не подменяет выход инструмента своими суждениями целиком — если профиль
  говорит «выборочно 10%», проверить 10%, не 100%.
- Не решает trust-уровень — он в профиле, задаётся на cold-start по опыту
  команды с инструментом.
