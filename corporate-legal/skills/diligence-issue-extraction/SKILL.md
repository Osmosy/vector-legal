# /diligence-issue-extraction — извлечение вопросов из dataroom (RF)

1. Прочитать `~/.hermes/legal/corporate-legal/CLAUDE.md` +
   `deal-context.md` дела.
2. Проверить `ai-tool-handoff` — если категория bulk и инструмент сконфигурирован,
   сначала handoff.
3. Прочитать документы, применить materiality-фильтр, извлечь по категориям.
4. Findings в house-формате memo. Передать с closing-actions в closing-checklist.

## Purpose

В dataroom 2000 документов. Где-то в них — 30, которые важны для сделки.
Навык читает документы против категорий и материальности из профиля,
извлекает вопросы и пишет их в house-формате memo.

## Load context

- Профиль → структура dataroom (категории, материальность)
- Профиль → формат issues memo
- `deal-context.md` → deal-специфичные пороги, расположение dataroom

Нет deal-context.md — спросить, для какой сделки.

## Workflow

### Шаг 1: Инвентаризация dataroom

Если VDR-коннектор (Box/Диск) подключён — pull индекс и смапить папки на
категории запросного листа. Отметить пробелы — категории без контента в
dataroom.

```markdown
## Инвентаризация dataroom: [код сделки]

| Категория запроса | Папка | Документов | Статус |
|---|---|---|---|
| Корпоративные | /01-Korporativnye | 45 | Просмотрено |
| Существенные договоры | /02-Dogovory | 312 | В работе |
| ФНС/налоги | /06-Nalogi | 28 | Не начато |
| [etc.] | | | |

**Пробелы:** [категории без документов — follow-up запрос]
```

### Шаг 2: Materiality-фильтр

По порогам профиля / deal-context. Не читать всё, если порог «договоры > X ₽».

Для договоров: сорт по стоимости (из имени/метадаты) или значимости
контрагента; просмотр сверху вниз до порога или исчерпания категории.

### Шаг 3: Извлечение вопросов

Для каждого документа — стандартный набор проверки по его категории.

**Существенные договоры — стандартный набор:**
- Оговорка о смене контроля (триггер этой сделкой? требуется согласие?)
- Ограничение уступки (договор переходит к покупателю? ст. 382/391 ГК)
- Эксклюзивность / неконкуренция (ограничивает бизнес покупателя?)
- MFN (ценовые ограничения)
- Права расторжения (контрагент может уйти из-за сделки?)
- Необычные indemnity / лимиты ответственности (неустойка ст. 330 ГК)
- Существенные условия и «существенные нарушения» — что контрагент может
  квалифицировать как существенное (ст. 450 ГК)

**Корпоративные — стандартный набор:**
- Реестр участников/акций: точность, корпоративный договор (ст. 67.2 ГК),
  акционерное соглашение (ст. 32.1 ФЗ-208), опционные соглашения (ст. 429.2 ГК)
- Одобрения по ст. 46/45 ФЗ-14 / ст. 79/84 ФЗ-208 на прошлые сделки: есть ли
  решения, оформлены ли правильно (кворум, порог, полномочия собрания)
- Устав: изменения, зарегистрированы ли, нет ли уставных ограничений на
  продажу долей (например, требование согласия общества/участников, ст. 21
  ФЗ-14 п. 10)
- Структура группы и intercompany-договоры

**ФНС / налоговые (специфика RF):**
- Истребования документов у самой организации (ст. 93 НК) и у контрагентов
  о ней (ст. 93.1 НК) за 3 года — были ли, какие темы, чем закончились
- Активные налоговые проверки (ст. 89 НК): этап, охват
- Доначисления за прошлые периоды, заявления о пересмотре
- НДС-вычеты по «проблемным» контрагентам (риск ст. 54.1 НК — деловая цель,
  реальность операций)
- УСН/ОСНО-режим, налоговые спец. режимы, консолидированные группы

**Трудовые:**
- Ключевые сотрудники: трудовые договоры, условия расторжения, компенсация
  при смене собственника (ст. 75 ТК — только руководитель, зам, главбух)
  `[verify]`
- Серые зарплаты, неоформленные сотрудники — риск
- Судебные споры с сотрудниками
- ПДн-обработка сотрудников (152-ФЗ)

**IP:**
- Цепочка прав: служебные произведения (ст. 1295 ГК), передача прав от
  фаундеров/сотрудников, регистрация ПО в Роспатенте
- Open source в продукте (copyleft-риск)
- Зарегистрированные ТМ/патенты, pending-заявки

**Судебные:**
- Активные дела и резервы (kad.arbitr.ru — сверка самостоятельно; споры
  в арбитражах и судах общей юрисдикции, ФССП-исполнительные производства)
- Регуляторные расследования (ФАС, ЦБ, РКН, Роспотребнадзор)
- Паттерн-споры (потребительские коллективные иски и т.п.)

**Лицензии:**
- Действующие лицензии и сроки (ФНС/ЦБ/отраслевые)
- Отзыв/приостановка/ограничения
- Для финансовых — пруденциальные требования ЦБ, предписания

### Шаг 4: Оформление каждой находки

> **Attribution источников.** Каждая находка со ссылкой на норму/дело/регулятора
> получает тег происхождения: `[КонсультантПлюс]`, `[kad.arbitr.ru]`,
> `[pravo.gov.ru]` — только если реально пришло из этого источника в сессии;
> `[web search — verify]` — из web-поиска; `[model knowledge — verify]` —
> из памяти модели; `[user provided]` — из дataroom/брифа/писем внешних
> юристов. Ссылки на документы dataroom (путь, имя файла) — нативная ссылка.
> Никогда не убирать и не схлопывать теги.

> **Расхождение с цитатой пользователя.** Если пользователь (или deal-team
> note, или sell-side письмо) цитирует норму, которая не выглядит верной, и
> текста нормы нет под рукой — не выдумывать описание: «Эта норма не совпадает
> с тем, что я ожидал бы от [типа нормы] — нужен текст, чтобы сказать, что
> она покрывает. `[норма не retrieved — verify]`» Дальше: (a) retrieve по
> КонсультантПлюс/Гарант, (b) попросить вставить текст, (c) флаг внешнему
> юристу. Уверенно-неверное описание действующей нормы хуже пробела.

> **No silent supplement.** Если поиск вернул мало/ничего по правовой основе,
> нужной находке — сказать, что нашли, и остановиться. Не заполнять пробел
> из web или памяти без спроса. Юрист решает, принимать ли источник меньшего
> доверия.

По шаблону из профиля. Если seed-мемо использовало этот:

```

 ходатайство ФАС / отказ от сделки]
```

...использовать именно его. Если seed был списком — писать списком.

**Калибровка severity (если дом — 🔴/🟡/🟢):**
- 🔴 **Красный:** влияет на цену или структуру сделки. CoC, требующий согласия
  крупного клиента. Незадекларированная материальная проверка. Пробел в правах
  на IP. Активная налоговая проверка с значимым доначислением.
- 🟡 **Жёлтый:** требует внимания, решаемо. Согласие требуется, но вероятно
  получаемо. Open source, требующий ремедиации. Риск переквалификации
  трудовых отношений.
- 🟢 **Зелёный:** заметка в файл. Соответствует заверениям. Действий нет, кроме
  отражения в заверении.

## Handoffs

- **К ai-tool-handoff:** если bulk-инструмент в профиле — передать туда
  объёмные категории. Этот навык — тонкие документы (side letters, доп.
  соглашения, всё, где инструмент слаб).
- **К deal-team-summary:** агрегированные находки кормят брифы.
- **К material-contract-schedule:** договорные находки кормят расписку.
- **К closing-checklist:** любая находка с pre-closing действием — в чеклист.
  Handoff не ограничен сторонними согласиями — это также:
  - **Корпоративные одобрения** — требуемые решения ОСУ/СД (ст. 46/45 ФЗ-14,
    ст. 79/84 ФЗ-208), отказы от преимущественного права, согласия супругов.
    Охарактеризовать действие, порог, норму, ограничение по времени.
  - **Регуляторные подачи** — ФАС (ст. 28-33 ФЗ-135), ЦБ, отраслевые.
  - **Согласия контрагентов** — CoC, анти-уступки, MFN-триггеры.
  - **Расторжения, releases, погашения** — employment releases, письма о
    прекращении, снятие обременений.
  - **Escrow/holdback** — если extraction вскрыл escrow (счёт эскроу ст.
    860.10 ГК), R&W-страховку, удержание из цены.
  Каждая находка с tag closing-action должна дойти до closing-checklist.
  Серые зоны — хэндоффить с флагом: closing-checklist отбросит лишнее.
  Под-хэндофф — односторонняя дверь; over-хэндофф исправляется ревью.

**Successor-risk (RF).** Флагнуть: возможные субсидиарные риски по
«продаже бизнеса» (не юрлица, а активов): перевод обязательств требует
согласия кредиторов для отдельных договоров, ст. 391 ГК; продажа
имущества должником перед банкротством — риск оспаривания (ФЗ-127 о
банкротстве, ст. 61.1+); налоговые долги остаются у юрлица-продавца, но
ст. 54.1 НК-риск реальности операций переносится по цепочке; лицензии не
передаются вместе с «бизнесом» — покупатель юрлица получает лицензии
вместе с юрлицом, покупатель активов — нет. Это анализ, который удивляет
клиентов, считающих «покупку активов» чистой `[каждый пункт — verify по
фактам структуры]`.

## Batch-обработка

Для больших категорий (300 договоров) — батчами. После каждого батча
обновлять running-список и флагать 🔴 немедленно — не ждать полной категории,
чтобы высветить влияние на сделку.

## Что дальше?

Decision tree из профиля. Кастомизировать: (1) передать находки в
closing/schedule; (2) draft запроса доп. документов sell-стороне; (3)
эскалация 🔴 аппруверу; (4) dashboard-предложение при >10 issues; (5) другое.

## Чего этот навык не делает

- Не делает materiality-вызов в пограничных случаях. Применяет порог;
  границу решает человек.
- Не ведёт переговоры по заверениям. Выдаёт находки, из которых их ведут.
- Не заменяет bulk-AI-ревью. По объёмной экстракции — handoff (см. профиль);
  навык — judgment-слой.
