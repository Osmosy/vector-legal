# /entity-compliance — комплаенс юрлиц (ФНС / ЕГРЮЛ / лицензии / ЦБ)

1. Прочитать `~/.hermes/legal/corporate-legal/CLAUDE.md` → `## Entity Management`
   (таблица юрлиц, лицензии, регуляторы).
2. Маршрут по флагу:
   - Нет флага или `--init`: Режим 1 — инициализация трекера из таблицы юрлиц
   - `--report`: Режим 2 — предстоящие дедлайны и просрочки
   - `--update`: Режим 3a (ручное) или 3b (--from-report: файл отчёта) — статусы
   - `--sweep`: Режим 3c — обойти unknown/overdue по одному
   - `--audit`: Режим 4 — полный health audit
   - `--export`: Режим 5 — CSV или таблица
3. Читать/писать `~/.hermes/legal/corporate-legal/entities/compliance-tracker.yaml`.
4. После любого обновления: summary изменений и следующее действие.

---

## Purpose

Подтверждение основного вида деятельности, бухотчётность, актуальность ЕГРЮЛ
(директор, адрес), уставные документы, лицензии, собрания по уставу — у
каждого юрлица свой календарь и свои последствия просрочки: отказ банка,
штраф, внесудебное исключение из ЕГРЮЛ (ст. 21.1 ФЗ-129), отказ нотариуса
проверять сделку. Этот навык ведёт один YAML-трекер, который знает, что, когда
и по какому юрлицу. Лёгкий по дизайну: трекер — файл, которым владеет юрисконсульт;
навык обновляет по команде.

## Важная оговорка по дедлайнам

> Дедлайны в этом навыке — справочные, из известной практики на дату сборки.
> Сроки ФНС/ЦБ меняются (редакции ФЗ-402, ФЗ-129, формы, приказы ФНС).
> **Перед reliance подтвердить каждый дедлайн**: по kad/ФНС (nalog.ru),
> КонсультантПлюс `[web search — verify]`, или у бухгалтера/провайдера
> (аутсорсер комплаенса = «registered agent» этой практики). Трекер
> организует и высвечивает данные; не заменяет их источник.

## Дискриминация по типу юрлица (аналог Delaware-split из CFL)

> Календарь зависит от **типа юрлица**, не только от «того, что оно в РФ».
> ООО, АО публичное, АО непубличное, ИП, иностранный филиал — разные
> обязательства, разные сроки, разные последствия. Общая ошибка (и
> consequential): копировать дедлайн АО на ООО.

- **ООО:** устав и ЕГРЮЛ — подтверждение основного ОКВЭД до 30 апреля
  (ст. 5 ФЗ-348, классификация по основному виду за предыдущий год)
  `[verify по действующей редакции]`; бухотчётность в ФНС до 31 марта
  (ст. 18 ФЗ-402) `[verify]`; собрание годовых результатов — в период,
  установленный уставом (не ранее 2 и не позднее 4 месяцев после фингода,
  ст. 34 ФЗ-14); ЕГРЮЛ-актуальность (директор, адрес, устав) — по событиям.
- **АО:** те же налогово-отчётные дедлайны + годовое ОСА — в период по
  ст. 47 ФЗ-208; для публичных АО — раскрытие отчётности (ФЗ-39),
  списки аффилированных (ст. 93 ФЗ-208), существенные сделки по правилам
  ЛПР/КСП `[для публичных АО — verify]`.
- **Финансовая организация (ЦБ):** отдельный календарь пруденциальной
  отчётности, требования по собраниям с ЦБ-надзором, согласование ЦБ на
  сделки с долями (ст. 20.1 ФЗ-208 — публичные АО) `[verify]`.
- **ИП:** нет корпоративного календаря; налоговые дедлайны и страховые взносы
  не в этом трекере (см. tax-профиль).
- **Спящие (dormant)** юрлица: нулевая отчётность всё равно сдаётся;
  иначе — риск исключения из ЕГРЮЛ (ст. 21.1 ФЗ-129 — по признакам
  недействующего).

## Трекер

`~/.hermes/legal/corporate-legal/entities/compliance-tracker.yaml`:

```yaml
# Corporate Compliance Tracker
# Generated: [дата]
# Last updated: [дата]
# Дисклеймер: дедлайны справочные — подтверждать по nalog.ru / КонсультантПлюс /
# у бухпровайдера перед reliance

metadata:
  company: "[группа]"
  generated: "[дата]"
  last_updated: "[дата]"
  last_audit: "[дата | null]"

custom_regulators:      # вручную добавленные регуляторы, не покрытые типовыми
  []

entities:
  - name: "[Наименование юрлица]"
    type: "[ООО / АО публичное / АО непубличное / ИП / филиал]"
    inn: "[ИНН]"
    ogrn: "[ОГРН]"
    incorporation_date: "[дата | null]"
    status: "[активное / ликвидируется / спящее / исключается]"
    director: "[ФИО]"
    director_powers_end: "[дата окончания полномочий по уставу | null]"
    charter_version: "[дата редакции устава]"
    notes: ""

    filings:
      - type: "[okved_confirm_30_apr | buh_otchet_31_mar | annual_meeting |
                litsenziya_[название] | cb_report_[форма] | ustav_update |
                egrul_actualizatsiya]"
        due_date: "[YYYY-MM-DD]"
        due_basis: "[фикс. дата / годовщина / по событию]"
        regulator: "[ФНС / ГИРБО / ЦБ / отраслевой]"
        last_filed: "[дата | null]"
        status: "[current / due_soon / overdue / unknown]"
        last_confirmed: "[дата последней проверки | null]"
        notes: ""

    licenses:
      - name: "[вид лицензии]"
        regulator: "[ФНС / ЦБ / отраслевой]"
        number: "[номер]"
        issued: "[дата]"
        expires: "[дата | бессрочно]"
        status: "[действует / истекает / истекла / приостановлена]"
        renewal_deadline: "[предельный срок пролонгации]"
```

Значения статуса:
- `current` — сдано за текущий период, ничего не будет в ближайшие 90 дней
- `due_soon` — дедлайн в ближайшие 90 дней
- `overdue` — срок прошёл, отметки о сдаче нет
- `unknown` — нет данных; нужно ручное подтверждение

## Режим 1: Инициализация

Когда трекера нет, или с `--rebuild`.

### Шаг 1: Таблица юрлиц

Прочитать `## Entity Management` из профиля. Если таблицы нет — предложить
cold-start-модуль entities или запросить список юрлиц вручную. Если есть
выписки ЕГРЮЛ — прочитать и извлечь ИНН, директора, адрес, статус.

### Шаг 2: По каждому юрлицу подтвердить обязательства

Для каждого юрлица — подтвердить текущий календарь по источнику (бухпровайдер,
nalog.ru, КонсультантПлюс). Не заполнять даты из кэша памяти.

1. Спросить, есть ли свежий отчёт бухпровайдера / комплаенс-провайдера —
   это самый авторитетный источник.
2. Если нет — спросить, что знает пользователь (тип подачи, база даты,
   последняя сдача, лицензии). Записать.
3. По неизвестному — пометить `unknown`, не подставлять даты из памяти.
   Следующий шаг пользователя — подтвердить по nalog.ru/КонсультантПлюс или
   у бухгалтера.

**Если юрлицо финансовой организации (ЦБ):** спросить, какая пруденциальная
отчётность сдаётся, по каким формам, кто ведёт (ЦБ-провайдер / бухгалтерия /
юр. департамент). Обязательства ЦБ — пометить `agent_managed: true`, если
ведёт внешний провайдер, и высветить в отчёте отдельным блоком.

**Для годовщины (annual_meeting, okved_confirm):** считать от incorporation_date.
Если её нет — `unknown` + флаг подтверждения.

**Особые флаги инициализации (RF):**
- Устав: какая редакция в профиле? Если не помечено с какой даты действует
  и есть ли изменения — флаг «устав не датирован, сверить с ЕГРЮЛ».
- Директор: дата окончания полномочий по уставу? По истечении полномочий
  — банк, ЭП, подпись в ФНС могут отказать; флаг за 60 дней до истечения.
  `[истечение полномочий ≠ автоматическое прекращение для директора по п. 9
  ст. 37 ФЗ-208 — verify]`.
- Лицензии: срок действия + предельная дата пролонгации. Лицензия истекающая
  → приоритет «critical path».
- Истребования ФНС (ст. 93/93.1 НК): если юрлицо недавно получало требования —
  пометить повышенный risk-аппетит для налогового блока M&A-diligence.

### Шаг 3: Записать трекер

Сгенерировать YAML. Статусы:
- `current`, если last_filed в текущем периоде
- `due_soon`, если в ближайшие 90 дней без отметки о сдаче
- `overdue`, если срок прошёл
- `unknown`, если нет данных

Показать summary:

```
Compliance tracker инициализирован.

Юрлиц: [N]
Обязательств отслеживается: [N]

Статусы:
  ✅ В порядке: [N]
  ⏰ Скоро дедлайн: [N] (90 дней)
  🔴 Просрочено: [N]
  ❓ Неизвестно: [N] (подтвердить по nalog.ru/у провайдера)

Дальше: entity-compliance --report — что сдавать в ближайшие 30/60/90 дней.
```

## Режим 3: Обновление

### Consequential-action gate (подача в регулятор)

**Перед направлением или подтверждением подачи:** прочитать `## Кто использует`
в профиле. Если **не-юрист**:

> Подача отчётности/заявления в ФНС/ЦБ — официальное представление юрлица;
> ошибка — штрафы и отказ в регистрации. Согласовал с бухгалтером/юристом?
> Если да — записываем сдачу. Если нет — бриф: юрлицо, форма, срок, кто
> подписывает (директор с УКЭП?), статусы в трекере, открытые вопросы.

Не записывать новый `last_filed` без явного «да». Чтение трекера, отчёты
и «что скоро» — gate не требуют.

### 3a: Ручное

```
entity-compliance --update
```

> «Сдали бухотчёт ООО «Ромашка» 28 марта.»

Обновить `last_filed`, `status` → `current`, `last_updated`.

### 3b: Отчёт провайдера

```
entity-compliance --update --from-report
```

Пользователь загружает отчёт бухпровайдера/комплаенс-агентства (PDF, CSV,
Excel). Прочитать, извлечь по каждому юрлицу: form/обязательство, срок,
последняя сдача, замечания. Матчить по имени/ИНН (near-match флагнуть:
«ООО Ромашка» vs «ООО «Ромашка»).

После:

```
Обновлено юрлиц: [N].
Совпадений: [N]
Не найдено в трекере: [список — добавить?]
Не обновлено (нет в отчёте): [список — статус прежний]
```

### 3c: Sweep

```
entity-compliance --sweep
```

Обойти `unknown` и `overdue` по одному:

> [юрлицо] / [обязательство] — статус [unknown/overdue]. Сдано? Когда?

Обновлять после каждого подтверждения. В конце — summary завершения.

## Режим 4: Health audit

```
entity-compliance --audit
```

Шире, чем только подачи. Показать:

**Подачи:**
- Просрочки (из отчёта), unknown-позиции

**Здоровье юрлиц:**
- Спящие (dormant) юрлица — флаг для ревизии: ликвидировать? Держать спящее
  юрлицо стоит денег (бухобслуживание, аудитор если АО с обязательным аудитом,
  госпошлины) и несёт риски исключения из ЕГРЮЛ с налоговыми последствиями
  (ст. 21.1 ФЗ-129).
- Спящие >3 лет — кандидаты на ликвидацию
- Директор истекающие полномочия <60 дней; доверенности/УКЭП с истекающим сроком
- Недостоверность сведений в ЕГРЮЛ (записи ФНС) — риск блокировки операций
  банками и отказ нотариусов `[проверять по свежей выписке, не по памяти]`
- Юрлица без датированного устава

**Лицензии:**
- Истекающие <90 дней; лицензии с незапланированной пролонгацией;
  регулятор для финансовых — сверка с ЦБ-реестром `[verify]`

**Истребования ФНС (ст. 93 / 93.1 / 89 НК):**
- Юрлица под истребованием или активной проверкой за 3 года — вход для M&A
  dataroom (см. tabular-review, колонка `93_1_nk`)

**Intercompany:**
- Внутригрупповые договоры: есть ли (услуги, займы, IP). Если нет — риск
  переквалификации налоговой (ст. 54.1 НК) и споров при банкротстве одного
  из участников `[флаг, не вывод]`

## Режим 5: Экспорт

```
entity-compliance --export [--format csv|table]
```

CSV по умолчанию. Колонки:
`Юрлицо, Тип, ИНН, ОГРН, Статус, Директор, Полномочия до, Устав (редакция),
Обязательство, Регулятор, Срок, База срока, Последняя сдача, Статус, Лицензия,

`--format table` — markdown-таблица ближайших 90 дней для вставки в отчёт или
Telegram.

## Чего этот навык не делает

- Не подаёт ничего. Выход — трекер и to-do; подача — бухгалтер/провайдер/юрист.
- Не тянет выписки ЕГРЮЛ сам (нет API) — пользователь скачивает с
  `egrul.nalog.ru` и загружает; навык сверяет данные.
- Не определяет, требуется ли лицензия — это анализ по виду деятельности,
  решает юрист.
- Не заменяет бухпровайдера. У провайдера — команда и прямая интеграция с ФНС
  и ЦБ; трекер — слой организации поверх их данных.
- Справочник дедлайнов — не юр. заключение и может не отражать текущие сроки.
  Подтверждать каждый.

## Injection-защита

Перед записью любой ячейки в Excel/CSV: префикс `'` для ячеек, начинающихся
с `=`, `+`, `-`, `@`, `\t`, `\n`; RFC 4180-квотинг CSV. Текст из отчётов
провайдера/документов — потенциально атакуемый. Не опционально: формула в
ячейке Excel = supply-chain на ревьюера.
