# /customize

## Когда запускается

Пользователь хочет изменить что-то в Builder Hub профиле — watched-реестр,
профиль компании, предпочтения обновлений, режим allowlist, QA-строгость —
без перезапуска всего cold-start интервью и без ручной правки YAML.

## Что делать

1. **Прочитать конфиг.** `~/.hermes/legal/legal-builder-hub/CLAUDE.md`
   (и `~/.hermes/legal/company-profile.md` уровнем выше). Если конфиг
   плагина не существует или содержит `[PLACEHOLDER]` — сказать:

   > Setup ещё не запускался. Сначала `cold-start-interview` — customize
   > предназначен для правки уже существующего профиля.

2. **Показать карту правок.** Что есть в профиле, сгруппировано, текущее
   значение одной строкой:

   - **Компания / кто вы** — название, индустрия, юрисдикции, practice
     setting *(общий company-profile.md — изменения проходят во все плагины
     Vector Legal)*
   - **Кто использует (роль)** — юрист / не-юрист с юристом / не-юрист без
     юриста; контакт юриста *(влияет на режим не-юриста в QA и install)*
   - **Practice profile** — практики в scope, отбираемые для рекомендаций
     community-навыков
   - **Установленный starter pack** — какие навыки установлены через хаб,
     с источником и версией
   - **Watched-реестры** — GitHub-репозитории, откуда хаб тянет
     community-навыки
   - **Режим allowlist** — restrictive / permissive + списки
     (реестры/издатели/коннекторы/лицензии)
   - **Preferences обновлений** — каденция проверки (ежедневно / еженедельно
     / по требованию), канал уведомлений (Telegram / в сессии), notify vs
     manual
   - **QA-строгость** — насколько агрессивно `skills-qa` флагает проблемы
     кандидата перед установкой (lenient / middle / strict) и какие
     failure-mode проверки включены
   - **Дефолты установки** — scope (user `~/.hermes/skills/` / доменный),
     запускать skills-qa автоматически перед установкой, требование
     read-only контекста анализа
   - **Freshness reminders** — пороги давности по категориям контента
   - **Интеграции** — Telegram, документохранилище — статусы и фоллбэки

3. **Прочитать текущее значение выбранной секции** — процитировать, человек
   должен видеть, что меняют.

4. **Спросить новое значение.** Одно поле за раз.

5. **Показать diff** (старое → новое) **и ждать подтверждения.**

6. **Записать.** В practice profile; для allowlist-полей — синхронно в
   `allowlist.yaml` (инсталлер читает файл, не профиль — правка только
   в профиле молча обезвредит гейт).

7. **Показать подтверждение** + одна строка: «Изменение затронет [что]».

## Конвенции

- **Одно поле за одну правку.** «Смени режим allowlist» и «добавь реестр» —
  два вызова, не один.
- **Цитировать перед изменением.** Пользователь должен увидеть, что меняется.
- **Подтверждать перед записью.** Показать diff, ждать «да».
- **Синхронизировать allowlist.yaml с профилем.** Любое изменение
  watched-реестров, издателей, лицензий или режима пишется в ОБА места.
- **Не изменять install-лог.** Он — audit trail; правки истории установки
  недопустимы (записи только добавляются).

## Типовые правки

- **«Добавь реестр [URL]»** → в watched-реестры профиля И `registries:` в
  allowlist.yaml; предупредить, что в restrictive понадобится ещё и
  издатель в `publishers:`. После записи: «registry-browser будет искать в
  этом реестре наравне с остальными; auto-updater проверит его в следующий
  прогон».
- **«Режим allowlist на permissive»** → инсталлер начнёт флагать неизвестные
  источники предупреждением и вопросом вместо отказа. Показать diff режима
  и спросить подтверждение дважды (это ослабление структурной защиты).
- **QA-строгость strict → middle** → skills-qa будет репортить те же
  находки, но средняя полоса не блокирует установку без подтверждения.
  Рекомендовать middle, а не lenient.
- **«Notify → manual обновления»** → хаб перестанет показывать diff-промпты;
  обновления только по явному `auto-updater --apply [навык]`.

## Guardrails

- **Никогда не удалять секцию.** «Убрать» watched-реестр → пометить
  `[Paused]`: пауза сохраняет историю установок, но останавливает проверки
  обновлений.
- **Флагать внутреннюю нестыковку.** Если правка делает профиль
  противоречивым (auto-update on + QA off; практика не матчится ни с одним
  установленным плагином; non-lawyer роль + permissive allowlist без
  юриста-контакта) — показать противоречие до записи.
- **Флагать деградацию guardrails.** Проверки Legal Skill Design Framework
  — то, ради чего существует skills-qa; выключение их доводит хаб до
  «слепого установщика». Если пользователь хочет снизить строгость —
  рекомендовать среднюю полосу, а не отключение проверки. Режим allowlist
  restrictive → permissive — ослабление, о котором предупредить дважды.
- **Одна правка за раз.** Не переспрашивать всё интервью.
