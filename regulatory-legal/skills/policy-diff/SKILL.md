# /policy-diff — diff НПА против политик

## Matter context

Проверить `## Matter workspaces` в practice profile; для firm — спросить,
по какому делу.

---

## Purpose

Новый акт вышел. Вопрос не «что он говорит», а «что из этого обязывает
НАС и чего нет в наших политиках». Diff — мост между дайджестом
(`reg-feed-watcher`) и планом соответствия (`gap-surfacer`,
`policy-redraft`).

## Загрузить контекст

1. `~/.hermes/legal/regulatory-legal/CLAUDE.md` — путь к библиотеке политик,
   materiality, отрасль
2. Текст акта: реквизиты, из задачи пользователя или
   `[web search — verify]` / `[pravo.gov.ru]` при реальном извлечении

## Scope integrity

Diff ровно против той политики, которую назвали. Не «сходить к соседней»
без запроса. Если название политики неоднозначно — показать список из
`## Policy library` и спросить.

## Workflow

### Шаг 0: Verify rule status before diff

До разложения на требования:

- **Статус:** принят/подписан/опубликован? Дата вступления? Что
  transitional? Проект ≠ закон (см. ветку Pre-rule ниже)
- **Источник:** реквизиты по pravo.gov.ru `[verify]`;
  `[web search — verify]` обязательно конвертировать в
  `[pravo.gov.ru]`-подтверждение перед тем, как строить план
- **Сфера:** применяется ли акт к отрасли компании вообще? Акт о
  маркировке рекламы не касается заводского цеха, если он не рекламирует

Не валидирован акт → не диффить: сказать, что нужно подтверждение, и
предложить web_search.

### Шаг 1: Extract the new requirements

Нумерованный список требований (не пересказ акта):

```markdown
**Требование N: [имя]**
- Норма: [статья/пункт]
- Суть: [одной строкой, человеческим языком]
- Кого касается: [все/операторы/отрасль/закупщики]
- Дата: [вступление/переходный срок]
- Тег: [pravo.gov.ru / web search — verify / user provided]
```

### Шаг 2: Map to policies

К каждой политике из библиотеки: какие требования адресует? Требования
вне политик — кандидаты на «новая политика нужна».

### Шаг 3: Diff

```markdown
### Требование [N]: [имя]
**Политика:** [имя/файл] | **Статус:** [✅ покрывает / 🟠 частично /
🔴 не покрывает / ⚪ нет политики]
**Что есть:** [раздел/цитата из политики]
**Чего не хватает:** [конкретный зазор]
**Вердикт:** [правка политики / новая политика / процесс вне политик]
```

### Шаг 4: No-match gaps

Требования без целевой политики — список «новая политика нужна», cada
черновик через `policy-starter` / `policy-redraft`.

## Branches by input type

### Pre-rule branch (проект НПА, публичное обсуждение)

Акт ещё не действует. Цель — проинформировать о направлении и дедлайне:

- Пометить в начале: «ПРОЕКТ, не действует; обсуждение до [дата]»
- Краткий разбор: какие изменения готовить заранее
- Лог в comment-tracker (если включён)
- **Не** создавать compliance gap — это pre-positioning. Полный diff —
  после публикации на pravo.gov.ru

### Negative-finding branch (акт не несёт зазора)

Diff показал полное покрытие — так это и записать: «Требование N покрыто
политикой [имя], правка не требуется». Не выдумывать пробелы ради плана.

## Выход

```markdown
[HEADER]

# Policy Diff: [НПА] — [Политика]

### Bottom line
[N требований · M пробелов · K покрыты; главная забота одной строкой]

### Summary
[Таблица требований: N · имя · статус · политика]

### Detailed diffs
[Подробные карточки из шага 3]

### Новые политики нужны
[Именованный список, каждая — наименование + зачем]

### No-gap requirements
[Однострочно, что уже покрыто — важно для аудиторского следа]
```

Передать дальше: пробелы → `gap-surfacer` (в gap-tracker), правки →
`policy-redraft`, проекты → `comments`.

## Close

Reviewer note (источники! статус акта! покрытие чтения) + decision tree:
1. **План соответствия** — приоритизированный список для юриста
2. **Redraft политики** — по конкретному пробелу
3. **Эскалировать** — если пробел срочный (дата близко)
4. **Дособрать факты** — что осталось непонятным
5. **Другое**
