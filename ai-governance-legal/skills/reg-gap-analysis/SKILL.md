# /reg-gap-analysis — gap-анализ нового требования

## Purpose

Новый регуляторный акт вышел (или заказчик требует соответствие ГОСТ по
ИИ). Задача: разложить его на требования, свести к текущему состоянию
компании, выдать план действий. Это рабочая таблица для юриста, не
правовое заключение.


---

## Shared guardrails (канон — practice profile)

**Reviewer note / decision tree / Destination check / Provenance /
No-silent-supplement / Currency trigger / Large input** — см.
practice profile (`~/.hermes/legal/<domain>/CLAUDE.md` → `## Shared
guardrails`, `## Outputs`). Блоки канонизируются там; если текст навыка
расходится с профилем — профиль контролирует.


## Загрузить текущее состояние

1. `~/.hermes/legal/ai-governance-legal/CLAUDE.md` — профиль
2. `~/.hermes/legal/ai-governance-legal/ai-systems.yaml` — какие системы есть
3. Файлы политики (из профиля), договоры с вендорами ИИ (если указаны)
4. Если профиль не заполнен — остановиться, попросить
   `cold-start-interview` или «provisional»

## Сначала research, потом workflow

До разложения требований — verify, что источник актуален:

- Текст НПА: поиск по pravo.gov.ru — официальный источник; тег
  `[pravo.gov.ru]` только при фактическом извлечении текста в этой сессии
- Статус ЭПР ИИ (ФЗ-123, Москва): `[verify]` — режим пилотный, детали
  могут меняться; проверять свежие публикации (mos.ru, Минэк)
- ГОСТ Р 59276-2020, ГОСТ Р ИСО/МЭК 23894 — добровольные: gap-анализ
  осмыслен, только если заказчик/тендер требует соответствие
- EU AI Act — для экспортных систем: даты применения по пакетам
  `[verify]` (2.02.2025 запреты, 2.08.2025 GPAI, 2.08.2026 high-risk —
  как ориентир; сверить с актуальным календарём)

**Если текст НПА не получен в этой сессии**: работать с формулировкой
пользователя, помечать всё `[user provided]` / `[model knowledge —
verify]` и предлагать web_search для подтверждения перед планом.

## Workflow

### Шаг 1: Scope regulation

> **Что за акт?** [название, номер, дата, кто принял]
> **На кого распространяется?** [юр. лица в РФ / операторы ПДн /
> заказчики ЭПР / экспортёры в ЕС]
> **Ключевая дата?** [вступление/переходный период]

Если акт не про ИИ/данные смежно — сказать и маршрутизировать:
регуляторика общего профиля → `regulatory-legal / reg-feed-watcher`.

### Шаг 2: Extract requirements

Разложить на нумерованные требования:

```markdown
**Требование #1: [короткое имя]**
- Норма: [статья/пункт]
- Что требует: [одна-две строки — по-человечески, не канцеляритом]
- Кого: [все компании / операторы ПДн / участники ЭПР]
- Штраф/санкция: [есть ли, размер]
- Тег источника: [pravo.gov.ru / КонсультантПлюс / user provided / model knowledge — verify]
```

### Шаг 3: Diff против текущего состояния

По каждому требованию:

```markdown
### Требование #N: [имя]
**Статус:** [✅ соответствует / 🟠 частично / 🔴 пробел / ⚪ невозможно
оценить без данных]
**Что есть:** [политика/контракт/процесс — с указанием файла]
**Чего не хватает:** [конкретика]
**Доказательство соответствия:** [каким документом подтвердить]
```

Уровень детализации — по масштабу требования: «назначить ответственного»
не требует diff-таблицы; «обеспечить локализацию данных» — требует.

### Шаг 4: Prioritize

| Priority | Критерий |
|---|---|
| 🔴 Критично | Штраф/блокировка деятельности; сроки до 3 мес.; данные клиентов |
| 🟠 Важно | Существенные операционные изменения; сроки 3–6 мес. |
| 🟡 Средне | Процессные улучшения; риск при проверке |
| 🟢 Низко | Документация, мониторинг |
| ⏸ Отложено | Не применимо сейчас [почему] |

### Шаг 5: Remediation plan

```markdown
# План соответствия: [Название НПА]

## Must-do до [дата вступления]
| # | Действие | Владелец | Срок | Зависимости |
|---|---|---|---|---|

## Should-do (важно, не блокирует)
## Уже соответствует
[Требования, закрытые текущим состоянием — с указанием чем]
## Принятые риски (не чиним)
[Осознанные пробелы — кто риск принял, когда пересматриваем]
```

## Исследование требования перед планом

Каждый пункт плана связан с требованием (шаг 2) и статусом (шаг 3).
Планы без требования «на всякий случай» — не добавлять. Если требование
спорное/двусмысленное — пометить `[требует правовой оценки]` и предложить
web_search или консультацию, не изобретать интерпретацию.

## Инеграция с другими навыками

- Требование про ПДн → детальный разбор в `privacy-legal`
- Изменения вендорских контрактов → `vendor-ai-review`
- Обновление политики → `policy-starter` / `policy-monitor`
- Трекинг выполнения → `gap-surfacer` в `regulatory-legal` (если
  подключён) или локальный трекер в профиле

## Выход

Один документ: план соответствия + Reviewer note + decision tree:
1. **Начать с 🔴** — первый пункт плана в работу
2. **Распределить** — разослать владельцам, эскалации
3. **Сохранить в трекер** — для периодической проверки
4. **Дособрать факты** — что не удалось понять из акта
5. **Другое**

## Чего не делает этот навык

- Не даёт «сертификации соответствия» — план готовит юрист
- Не интерпретирует спорные нормы бесспорно — помечает `[требует правовой
  оценки]`
- Не заменяет чтение полного текста акта: >50 стр. — фиксировать покрытие
  в Reviewer note (какие статьи прочитаны) и предлагать фокусную выборку
