# /policy-monitor — мониторинг ИИ-политики

## Purpose

ИИ-политика — живой документ. Плагины, системы и практика меняются быстрее,
чем политика. Навык работает в двух режимах:

1. **Sweep** — регулярная проверка политики на пробелы против реестра
   систем, реестра use-case'ов и текущей регуляторики
2. **Direct query** — «разрешает ли наша политика эту [практику]?»

## Загрузить текущее состояние

1. `~/.hermes/legal/ai-governance-legal/CLAUDE.md` — профиль (реестр
   use-case'ов, red lines, governance tiers)
2. `~/.hermes/legal/ai-governance-legal/ai-systems.yaml` — реестр систем
3. **Файлы политики** — путь из профиля (`## Impact assessment house
   style` или отдельный `Policy documents location`). Если не задан —
   спросить: «Где лежит политика? Файл/путь/вставленный текст?»

## Определение режима

- Был запущен со словом `sweep` / по расписанию / без аргумента → Sweep
- Был запущен с описанием практики или вопроса → Direct query

## Режим 1: Sweep

### Определить охват

Спросить или взять дефолт: «Полная политика или раздел?» Если политика
разбита на файлы (приемлемое использование, ПДн, безопасность, закупки) —
предложить полный sweep или один раздел.

### Что читать для каждого типа выхода

- Реестр систем: `ai-systems.yaml` — появились ли системы, которых
  политика не знает
- Реестр use-case'ов: появились ли use-case'ы вне категорий политики
- Регуляторные обновления: свежие НПА, влияющие на ИИ-политику. Проверять
  web_search по запросу вроде «экспериментальный правовой режим ИИ
  изменения 2026» / «приказ РКН персональные данные ИИ» — результаты
  тегировать `[web search — verify]`. ЭПР ИИ (ФЗ-123) и ГОСТ Р 59276-2020
  — динамические точки `[verify]`
- Заказные требования: тендерные ТЗ, где фигурируют ГОСТ Р 59276-2020 или
  ГОСТ Р ИСО/МЭК 23894, — политика должна уметь ответить «как мы
  обеспечиваем доверие ИИ» (добровольное, но встречается в закупках)

### Идентификация пробелов

Для каждого элемента (система, use-case, регуляторное требование) спросить:
- Политика это покрывает? (да — частично — нет)
- Если частично — какие аспекты не покрыты?
- Если нет — насколько срочно?

### Формат выхода Sweep

```markdown
[TIER HEADER — по профилю]

# AI Policy Monitor — Sweep Report

## REQUIRED updates
### [Пробел 1]
**Что:** [пробел одной строкой]
**Почему это пробел:** [какой реестр-элемент или требование не покрыт]
**Риск:** [что происходит, пока пробел открыт]
**Фикс:** [1–2 строки — что добавить, ссылка на раздел политики]

## ADVISABLE updates
### [Пробел]
[То же, меньше срочности]

## No action needed
[Проверено, покрыто — одной строкой список]

## Sync реестра use-case'ов
[Записи, которые стоит добавить/обновить в профиле]

## Следующий шаг
[route: policy-starter для новых разделов / customize для правки профиля /
reg-gap-analysis для нового НПА / юрист для решения]
```

## Режим 2: Direct query

### Парсинг предлагаемой практики

Из запроса пользователя: что за система/действие, данные, кто затронут,
какой governance tier. Не хватает — 1–2 уточняющих вопроса, не больше.

### Diff политики

Прочитать политику (раздел за разделом): где эта практика явно разрешена,
явно запрещена, молчит?

### Формат выхода Direct query

```markdown
[TIER HEADER]

# AI Policy Check: [Практика одной строкой]

## Что покрыто
[Ссылки на разделы политики — цитировать]

## Чего не хватает
### [Пробел]
Политика молчит на [аспект]. Варианты: [запретить / разрешить с условиями /
эскалировать для решения]
```

Завершить decision tree: обновить политику (`policy-starter`), эскалировать,
записать условие в governance tier, наблюдать.

## Границы

- Не переписывать политику в этом навыке — для этого `policy-starter`
  (новая политика) и `policy-redraft` — при наличии; здесь — только
  находка пробела и рекомендация направления
- Не выводить «политика соответствует закону» — проверка соответствия
  требует юриста; навык находит пробелы, не даёт заключений

## Close

Reviewer note (один блок) + decision tree «Что дальше?» — по формату из
practice profile.
