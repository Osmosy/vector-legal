# /vendor-ai-review — ревизия ИИ-соглашений с вендорами

## Matter context

Проверить `## Matter workspaces` в practice profile; если включено —
спросить, для какого дела.

---

## Purpose

Вендорский ИИ-контракт — обычный SaaS-договор плюс ИИ-специфика,
которой нет в шаблонах: обучение на наших данных, права на выходы,
ответственность за качество модели, субпроцессоры, трансграничная
передача. Задача — пройти термин за термином и выдать redline'ы по
playbook.

## Загрузить playbook

1. **Прочитать** `~/.hermes/legal/ai-governance-legal/CLAUDE.md`. Плейсхолдеры
   → `cold-start-interview` или «provisional» для generic-ревизии с метками
   `[PROVISIONAL]`
2. Прочитать также **позиции по 152-ФЗ** из профиля (раздел «Проверка
   использования ПДн») и, если есть, seed-договоры с ИИ-вендорами

## Перед чтением документа

Спросить (или извлечь из контекста):
- Что покупаем: API к модели / SaaS с ИИ-фичей / кастомная разработка?
- Какие данные пойдут в систему (сейчас и по плану)? Есть ли ПДн?
- Кто наши клиенты в выхлопе системы? Экспортный рынок (eu_nexus)?

## Ревизия по терминам

### Ядро ИИ-специфичных терминов (проверять в каждом)

1. **Обучение на наших данных** — дефолт вендора: «можем использовать для
   улучшения сервисов». Требование playbook обычно: opt-out или запрет.
   Если запрет — проверить формулировку: «use Customer Data to train»
   шире «train» — ловить промпты, телеметрию, feedback-петли
2. **Ownership выходов** — кому принадлежит результат? По ГК результаты
   генерации: охраноспособность спорна (создано без человека-автора —
   ст. 1257 ГК), но права по договору распределять нужно всё равно
   (ст. 1233+ ГК — лицензионные конструкции)
3. **Ответственность за дефекты модели** — вендоры капают всё и дисклеймят
   warranty. Против ст. 15, 401 ГК: не всякое ограничение в РФ-контракте
   валидно (п. 4 ст. 401 ГК — императив для умысла); проверить индемнити
   за IP-претензии по выходам
4. **Субпроцессоры / подрядчики** — список, уведомление, право возражения;
   по 152-ФЗ ч. 3 ст. 6 — поручение
5. **Трансграничная передача** — где инфраструктура? ст. 12 152-ФЗ +
   приказ РКН №931; для многих вендоров вывод в РФ-контуре — сделка
   невозможна без локального контура — флагнуть сразу
6. **ИИ-регуляторные обязательства вендора** — для eu_nexus: кто провайдер
   по ст. 2(с) EU AI Act? Вендор передаёт обязанности деплойера?

### Общие коммерческие термины (сквозные, проверять при наличии)

- Лимит ответственности (4 позиции — см. commercial-legal playbook)
- SLA и credit'ы
- Term, расторжение, exit и миграция данных
- Апдейты модели: может ли вендор заменить модель под капотом и что
  происходит с нашими промптами/данными
- Confidentiality: наши промпты — наша КТ?

## Сравнение с playbook

По каждому термину: позиция playbook → позиция вендора → gap → severity →
конкретная редакция правки (не «рассмотреть возможность»). Именованный
аппрувер для 🔴/🟠 из матрицы эскалаций.

## AI addendum gap check

Если вендор присылает «AI addendum» к старому договору:
- Какие пункты основного договора остаются в силе и противоречат
  аддендуму (автопродление, передача данных третьим лицам)?
- Кто побеждает при конфликте — порядок приоритета документов?
- Поручение на обработку отдельно или в аддендуме (если ПДн уходят)?

## Соответствие ИИ-политике

Сверить соглашение с `## Use case registry` и red lines профиля: если
вендор требует обучения на данных, которое нарушает red line — стоп и
эскалация, не «договоримся в redline».

## Гранулярность redline

Слово → фраза → подпункт → пункт → раздел: минимальная правка, достигающая
позиции playbook. Wholesale-замена — сигнал агрессии и потеря хороших
частей драфта. В сомнении — меньше. Для «обучения на наших данных» —
часто достаточно вычеркнуть слово «улучшение» из перечня целей использования.

```markdown
|---|---|---|---|---|---|

## AI addendum и субпроцессоры
[Статус, пробелы, список субпроцессоров]

## 152-ФЗ статус
[Основание обработки, поручение, локализация, трансграничка — pass/fail
по каждому; вектор приказа №180, если применим]

## Экспорт-контур (если применимо)
[Роли EU AI Act, обязанность деплойера, что должно остаться за вендором]

## Рекомендуемые redline'ы
[Топ-5, по приоритету, конкретными редакциями]

## Если не сдвинутся
[Фоллбэки из playbook / выйти из сделки / эскалация]

## Практические заметки
[Что проверить до подписи, каких вопросов вендору ожидать]
```

Затем — Reviewer note и decision tree:
1. **Приложить redline** для контрагента
2. **Эскалировать** 🔴/🟠 аппруверу
3. **Протокол разногласий** — draft (см. commercial-legal)
4. **Отказ** — короткий memo «почему нет»
5. **Другое**

## Чего не делать

- Не выдавать «сделка в порядке» — выход всегда черновик юристу
- Не редактировать пункты без цитаты вендорского текста
- Не пропускать 152-ФЗ блок: «вендор GDPR-compliant» ≠ 152-ФЗ
- Не делать вывóды по лицензиям на выходы без проверки текста лицензии
  вендора в этой сессии (`[user provided]` или `[web search — verify]`)

**Теги источников:** нормы 152-ФЗ и ГК — `[КонсультантПлюс]` при
проверке в сессии, иначе `[model knowledge — verify]`; реквизиты вендора
и тексты договора — `[user provided]`; EU AI Act ссылки —
`[verify]` (проверять текст акта).

## Чего не делает этот навык

- Не заменяет полный ревизию коммерческих терминов — для этого
  `commercial-legal / vendor-agreement-review` поверх этого
- Не оценяет качество модели — только договорные механизмы
- Не консультирует по зарубежному праву вне EU-модуля
