# /supervisor-review-queue — очередь супервизора

1. Прочитать `~/.hermes/legal/legal-clinic/CLAUDE.md` → супервизорская модель.
   Если НЕ «формальная очередь»: объяснить, что клиника настроена на
   [флаги/лёгкий режим] — формальной очереди нет, показать как устроен
   супервизорский контроль в этой модели и как переключиться. **Напомнить:
   подпись супервизора обязательна при любой модели (SUPERVISOR-GATE).**
2. Использовать workflow ниже.
3. Дефолт: показать, что ждёт, по уровню риска и по студенту.
4. Действия: approve / edit-then-approve / return с комментарием. Всё логируется.

```
supervisor-review-queue
```

```
supervisor-review-queue --approve Q-003
```

```
supervisor-review-queue --return Q-004 "Проверь расчёт срока по ст. 392 ТК — копия приказа от [дата], не от даты разговора"
```

# Очередь супервизора

## Назначение

Часть клиник хотят жёсткие ворота: студент готовит — супервизор проверяет —
документ выходит. Часть считают это излишне формальным: супервизия через
кейс-раунды и один-на-один.

**Этот навык активен, только если в
`~/.hermes/legal/legal-clinic/CLAUDE.md` → Супервизорская модель стоит
«формальная очередь».** Иначе спит — cold-start предлагает супервизору выбор
из трёх механик.

**Важно: выбор механики не отменяет SUPERVISOR-GATE.** НИЧТО не уходит к
клиенту, в суд или ведомство без подписи супервизора — при любой из трёх
моделей. Очередь — механика, не источник полномочий.

## Load context

`~/.hermes/legal/legal-clinic/CLAUDE.md` → супервизорская модель. Если НЕ
«формальная очередь» → «Клиника настроена на [флаги/лёгкий режим] — формальной
очереди нет. [Супервизор] проверяет через [существующую структуру]. Чтобы
включить очередь, правь CLAUDE.md → Супервизорская модель. Подпись на
исходящем обязательна при любой модели.»

Если очередь включена → прочитать триггеры и продолжать.

## Теги риска

Каждый пункт очереди несёт тег уровня риска — супервизор видит с первого
взгляда, что проверять внимательно:

| Тег | Уровень | Типичные ситуации |
|---|---|---|
| 🔴 | блокирующий | процессуальные документы в суд/ведомство; миграционные и семейно-ДВ категории; любые сроки, истекающие в ближайшие 7 дней; конфликт интересов |
| 🟠 | высокий | письма клиенту с правовым содержанием; заключения по делам с встречными требованиями; дела, где клиент уязвим (возраст, язык, состояние) |
| 🟡 | средний | рутинная переписка по делам с активными сроками; intake-резюме с кросс-категорийными флагами; статусы клиенту |
| 🟢 | низкий | приглашения на приём; запросы документов без сроков; справки о работе клиники |

**Масштаб канонический для всего плагина** (см. CLAUDE.md → Shared guardrails);
если исходная оценка из другого навыка спорна, округление ВВЕРХ. Понижение
тега при маршрутизации — только с явной строкой: «Пришло как [X], понижаю до
[Y], потому что [причина]». Молча занижать нельзя (cross-skill severity floor).

## Очередь

Живёт в `~/.hermes/legal/legal-clinic/review-queue.yaml`. Каждый пункт:

```yaml
- id: Q-001
  type: "draft"  # intake | draft | memo | status | client-letter
  client: "[ФИО или ID]"
  student: "[имя]"
  submitted: [timestamp]
  risk: "🔴"   # 🔴 | 🟠 | 🟡 | 🟢
  risk_reason: "[почему этот уровень]"
  flags:
    - rule: "Процессуальный документ"
      detail: "Возражения на иск о выселении — всегда в очередь"
  content_path: "[путь к документу]"
  status: "pending"  # pending | approved | edited-approved | returned
  signed_by: null    # ФИО супервизора после подписи
  signed_at: null
```

## Режимы

### Что ждёт

```markdown
## Очередь супервизора — [дата]

**Ждут:** [N] | **Старейший:** [N] часов | **🔴 блокирующих:** [N]

### 🔴 Блокирующие (процессуальные документы, сроки, чувствительные категории)
| ID | Тип | Клиент | Студент | Почему флаг | Риск-тег | Ждёт |
|---|---|---|---|---|---|---|

### 🟠 Высокий
[та же таблица]

### 🟡 Средний
[та же таблица]

### 🟢 Низкий
[та же таблица]

### По студентам
[Разбивка — ловить паттерны: кто часто в очереди, кому нужен чек-ин]
```

### Разбор пункта

Показать содержимое полностью + почему флагнуто + заметки студента.

### Approve / edit-then-approve / return

- **Approve:** статус → `approved`, `signed_by: [супервизор]`,
  `signed_at: [дата]`; студент уведомлён; залогировано.
- **Edit then approve:** супервизор правит inline; одобренная версия —
  правленая; оригинал сохраняется в логе, студент видит diff (обучающий
  момент).
- **Return:** с комментарием. Студент дорабатывает и сдаёт заново.

## Логирование

Каждое действие логируется. Логи одобрений — документы клиники: они
фиксируют, что квалифицированный юрработник проверил работу студента до того,
как она ушла клиенту, в суд или ведомство. Это важно и для комплаенса
клиники, и для оценки студентов.

## Обучающий сигнал

Очередь — тоже данные. Паттерн возвратов («студент X путает срок по ст. 392
ТК с претензионным») — коучинговый разговор. Паттерн правок («у всех письма
клиентам слишком длинные») — апдейт `/ramp` на следующий семестр.

## Что этот навык НЕ делает

- **Не запускается, если супервизор его не выбрал.** Одна из трёх механик,
  не единственная.
- **Авто-одобряет.** Одобряет супервизор.
- **Не заменяет существующую супервизию клиники.** Ворота для work product,
  не замена кейс-раундов, один-на-один и наблюдения за студентами.
