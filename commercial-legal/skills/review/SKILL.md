# /review — маршрутизация ревизии договора

Разбирает входящий договор против playbook в
`~/.hermes/legal/commercial-legal/CLAUDE.md`. Определяет структуру документа
по заголовкам, выбирает профильный навык(-и) и — если `confirm_routing`
включён — сверяется с пользователем до начала.

## Инструкции

1. **Загрузить `~/.hermes/legal/commercial-legal/CLAUDE.md`.** Если есть
   плейсхолдеры — остановиться и спросить: «Плагин не настроен. Запусти
   `cold-start-interview` — мне нужно выучить ваш playbook, иначе ревизия
   будет generic». Либо пользователь говорит **«provisional»** — тогда
   ревизия против generic дефолтов РФ с метками `[PROVISIONAL]` (см. README
   плагина) [model knowledge — verify].

2. **Получить договор:** путь к файлу, ссылка, вставленный текст. Если ничего
   — спросить.

3. **Прочитать структуру документа — сначала заголовки.** До тела извлечь:
   - Название основного договора («Договор поставки», «Договор возмездного
     оказания услуг», «Master Services Agreement», «Соглашение о
     неразглашении»)
   - Заголовки всех приложений («Приложение №1 — DPA», «Спецификация №1»,
     «Техническое задание»)

   Это сигнал маршрутизации. Не опираться на ключевые слова в теле: договор
   поставки на 40 страниц со словом «конфиденциально» по всему тексту — не NDA.

4. **Выбрать навык(-и) по структуре.**

   | Заголовок содержит | Навык |
   |---|---|
   | Неразглашение, конфиденциальность (как **основной** договор) | **nda-review** |
   | Поставка, подряд, возмездное оказание услуг, MSA, Professional Services | **vendor-agreement-review** |
   | Лицензия на ПО, SaaS, подписка, телематические услуги, Order Form с автопродлением | **saas-msa-review** (поверх vendor-agreement-review) |
   | Поручение на обработку ПД, DPA (приложение или отдельный документ) | заметка для **vendor-agreement-review** → раздел 152-ФЗ [pravo.gov.ru] |
   | SLA (приложение) | заметка для **saas-msa-review** → раздел SLA |

   Несколько навыков могут применяться вместе. Частые комбинации:
   - Договор услуг + DPA приложением → vendor-agreement-review с заметкой DPA
   - Лицензия на ПО + Order Form + SLA → saas-msa-review (покрывает все три)
   - Договор + спецификация с автопродлением → vendor-agreement-review

   Если тип неоднозначен после заголовков — прочитать первые 2 страницы тела
   для разрешения, затем маршрутизировать.

5. **Подтвердить маршрутизацию** (если `confirm_routing: true`):

   ```
   Ревизую как: [тип(-ы) договора].

   Определены документы:
   - [Название основного] → [навык]
   - [Приложение №1 — DPA] → заметка в [навык]

   Подтверждаешь? [Да / Изменить маршрутизацию]
   ```

6. **Выполнить выбранный навык(-и)** и интегрировать выходы в **одно memo**:
   сквозная таблица findings (дедуп между навыками), severity по общей
   шкале (🔴 Blocking / 🟠 High / 🟡 Medium / 🟢 Low × правовой риск / бизнес-
   трение), именованный аппрувер из матрицы эскалаций для каждого 🔴/🟠.

7. **Reviewer note + decision tree** — по формату из practice profile
   (`⚠️ Reviewer note` один блок сверху, затем deliverable, затем
   `Что дальше?`).

## Shared guardrails (канон — practice profile)

**Reviewer note / decision tree / Destination check / Provenance /
No-silent-supplement / Currency trigger / Large input** — см.
practice profile (`~/.hermes/legal/<domain>/CLAUDE.md` → `## Shared
guardrails`, `## Outputs`). Блоки канонизируются там; если текст навыка
расходится с профилем — профиль контролирует.


## Выход

Memo в формате навыка(-ов). Routing-решение зафиксировано наверху.
Отклонение за отклонением — с конкретной редакцией правки, именованный
аппрувер. Сохранить туда, куда указывает House style профиля.

## Сторона договора

Перед применением playbook определить сторону компании (см.
`## Playbook → Active side` в профиле). Для этого плагина обычно «закупки»,
но проверить: «договор подряда» может быть нашим шаблоном, отправленным
подрядчику. Если неочевидно — спросить.
