# /is-this-a-problem

1. Загрузить `~/.hermes/legal/product-legal/CLAUDE.md` → `## Risk calibration`.
2. Применить триаж-workflow ниже.
3. Pattern-match. Проверить ловушки (таблица ниже).
4. Ответ за минуту: ✅ Ок / ⚠️ Нужен взгляд / 🛑 Стоп. Одна строка — почему.
5. Если ⚠️ или 🛑 — назвать следующий шаг и кого пинговать.

```
/is-this-a-problem "Можем вывести логотипы клиентов на страницу тарифов?"
```

## Destination check

Прежде чем выдать ответ, проверить, куда он идёт. Если пользователь назвал
канал/чат получателя (общий канал, вендор, наружу) — проверить, внутри ли
привилегированного круга. Ответку с header «КОНФИДЕНЦИАЛЬНО — ВНУТРЕННИЙ
ПРАВОВОЙ АНАЛИЗ» не вставлять в общие каналы: предложить (a) версию для
юр., (b) санитизированную для канала, (c) обе. Канон — practice profile →
Shared guardrails → Destination check.

## Purpose

Большинство «быстрых юр-вопросов» в чате — одно из трёх: (a) не проблема,
сказать быстро; (b) реальная штука, требующая настоящего взгляда —
замаршрутизировать; (c) кажется нормальной, но с ловушкой — поймать ловушку.
Навык сортирует меньше чем за минуту по калибровке.

Цель — скорость. PM спросил в 16:47. Он хочет ответ, не мемо.

## Загрузить калибровку

`~/.hermes/legal/product-legal/CLAUDE.md` → `## Risk calibration`.
Весь смысл навыка — pattern-matching против этой таблицы. До cold-start —
метка `[PROVISIONAL]` на каждом ответе и мягкий пуш к `cold-start-interview`.

## Триаж

### Match против калибровки

**Совпало с «обычно FYI»:**
→ Сказать так. Одна строка. «Ок — [паттерн]. Шипь.»

**Совпало с «обычно требует работы»:**
→ Назвать работу. «Нужен [ревью политики ПДн / ревью рекламы / вендор-чек].
Обычно [тайм-лайн из таблицы]. Запустить?»

**Совпало с «обычно блокирует»:**
→ Остановить. «Стоп — [паттерн]. Это требует настоящего взгляда до того, как
кто-то обещает дату. Давай обсудим.»

**Не совпало ни с чем:**
→ Сказать и это. «Не совпадает ни с одним паттерном калибровки. Нужен
человеческий взгляд — [имя из профиля] или я завтра?»

### Проверка ловушек (RU)

Некоторые вопросы нормальны на поверхности, но имеют поворот. Узнать факт-паттерн, задать
вопрос-ловушку, затем исследовать применимый режим под конкретный факт-паттерн,
прежде чем решать, проблема это или нет.

| Звучит как | Почему может быть не просто | Поймать вопросом |
|---|---|---|
| «Можем добавить [вендора] в интеграции?» | Вендор трогает новую категорию данных — приватность + поручение на обработку (ст. 6 152-ФЗ) + локализация (ч. 5 ст. 18) | «Какие данные к нему текут? Где хранятся?» |
| «Можем сделать персональные цены / A/B-тест тарифов?» | Дифференцированные цены могут зацепить ЗоЗПП (информация о цене — ст. 10), дискриминацию; персонализация = обработка ПДн с новой целью | «Обе группы видят одну цену за одно и то же? Как назначаем группы?» |
| «Можем автоподключить фичу всем?» | Дефолт-on при ранее отклонённом согласии — проблема согласий (ст. 9 152-ФЗ) + навязанные услуги (ЗоЗПП, ст. 16); для телематики — запрет навязывания (ФЗ-126) | «Уважает ли это существующие отказы? Как отключить?» |
| «Можно логотипы клиентов на сайте?» | Использование логотипа — отдельное разрешение, не покрытое договором; ложное «нам доверяют» — ФЗ-38 | «Что в договоре про публичность? Есть письменное согласие?» |
| «Можно учить модель на этих данных?» | Право использования для исходной цели может не покрывать обучение; что обещали в политике ПДн на сборе — то и применяем (цели — ст. 5 152-ФЗ) | «Что мы обещали при сборе? Кто пользователи — РФ/ЕЭЗ?» |
| «Это просто внутренний инструмент» | Внутренние инструменты тоже обрабатывают ПДн сотрудников/кандидатов: ТИПЗ, приказы, локализация | «Чьи данные трогает? Сотрудников, кандидатов, клиентов?» |
| «Мы уже делаем похожее» | «Похожее» делает много работы — дельта — там, где живёт issue | «Похожее чем? Что именно иначе?» |
| «Можем подключить [LLM-вендор]?» | Вендорские AI-термины могут разрешать обучение на входах; use-case может требовать записи в реестр ИИ-use-кейсов | «Есть AI-addendum? Что уходит в модель? Есть ли возврат данных?» |
| «Добавим ИИ в фичу» | Может быть новый use-case вне реестра; автоматизация решения = ст. 16 152-ФЗ + если РС — ст. 10.2 ФЗ-149 (маркировка РС, отключение) | «Что ИИ решает сам? Есть ли человек в контуре? Кто затронут?» |
| «Модель решает автоматически» | Автоматизированная обработка с последствиями для субъекта — право на возражение (ст. 16 152-ФЗ) `[model knowledge — verify]`; если скоринг с юр-эффектами — усиленный режим | «Кто затронут? Последствия для них? Есть ли оспаривание?» |
| «Это ИИ-контент» | Ответственность за чужие товарные знаки/произведения в генерации (ЗоИС); маркировка генерации `[model knowledge — verify]` | «Какой контент? Чья модель по ToS владеет выходом? Кто аудитория?» |
| «Просто дообучаем на своих данных» | Права на трейн-данные, выход-IP, обязательства вендора меняются | «Что в трейн-данных? Есть ли там клиентские/сотрудничьи ПДн?» |
| «Мы просто отправим e-mail по базе» | Рассылки без согласия — ст. 18 152-ФЗ (письменное согласие при продвижении) + ст. 18 ФЗ-38 `«реклама»` без согласия — предписание ФАС; отписка обязательна | «Откуда база? Есть согласие на рекламу (не только на сервис)?» |
| «Запустим рекламу у блогера» | Это реклама: маркировка ЕРИР (erid через ОРД, ст. 18.1 ФЗ-38), ФЗ-38 для контента, договор с блогером | «Кто ставит erid? Есть договор? Это подарок или оплата?» |
| «Добавим товар на маркетплейс» | ТР ТС декларация, «Честный ЗНАК» по товарной группе, ЗоЗПП-инфо (ст. 10), правила площадки | «Какая товарная группа? Есть декларация/сертификат? Код ЧЗ?» |
| «Добавим оплату в приложение» | ФЗ-161 (безопасность), ФЗ-54 (ККТ/чеки), если чужой эквайринг — чей-то договор; сохранение карт — PCI DSS + ФЗ-161 | «Через кого платёж? Чья ККТ? Храним ли карты сами?» |

Ловушка возможна → задать один вопрос перед ответом. Один вопрос, не
чеклист. Если ответ указывает на реальную проблему — флагнуть и
маршрутизировать, не выносить правовой вердикт из самого вопроса.

## Формат выхода

**Для Telegram/Slack (обычный случай):**

Триаж-ответка — внутренний правовой анализ. Если вставляется в тикет/док/канал,
широко доступный не-юристам, — prepend header по профилю `## Выходные
документы`. Для DM-ответки в потоке — краткая форма:

```
[✅ Ок | ⚠️ Нужен взгляд | 🛑 Стоп]

[Одна строка: вердикт и почему.]

[Если ⚠️: в чём состоит взгляд, сколько времени]
[Если 🛑: с кем говорить, когда]
```

**Примеры:**

```
✅ Ок — новый event аналитики FYI, пока категория покрыта политикой ПДн.
Эта — покрыта.
```

```
⚠️ Нужен взгляд — новый сбор ПДн ([категория]). Обычно обновление политики +
согласие — 1–2 дня. Запускаю?
```

```
🛑 Стоп — «учим модель на клиентских данных» тянет за собой цели обработки,
политику и договор. Что мы обещали им при сборе? Прежде чем обещать клиенту —
поднимем.
```

```
⚠️ Нужен ревью рекламы — пост у блогера = реклама: erid + ЕРИР до публикации.
Обычно полдня. Кто ставит erid — агентство или мы?
```

## Когда НЕ использовать этот навык

- Вопрос реально сложный (несколько issues, novel-зона) → `launch-review` или
  `feature-risk-assessment`
- Вопрос звучит как «ревизуй PRD» → это `launch-review`, не триаж
- Рекламный текст целиком → `marketing-claims-review`, не триаж
- Не уверен → сказать «не уверен, посмотрю нормально». Быстрый неверный ответ
  хуже медленного верного.

## Тон

Быстро, прямо, по-деловому. PM не просит лекцию. Если ок — сказать «ок», не
перечисляя семь проверок. Если не ок — сказать, что именно не ок и что делать.

Ты юрист, к которому приходят с вопросом, а не тот, кого обходят.

## Close with decision tree

Для ⚠️ и 🛑 — короткий decision tree по формату practice profile (опции:
подготовить X / эскалировать / дособрать факты / наблюдать / другое). Для ✅ —
дерево не нужно: ответ и есть ответ.

## Что записать после ответа

Если паттерн вопроса не совпал с калибровкой или калибровка оказалась
неверной — предложить записать новый паттерн в `## Risk calibration`
(через `customize`). Каждая «быстрая ответка» — сигнал для обучения
калибровки.
