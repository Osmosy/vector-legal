# /document-anonymize — обезличивание перед внешней отправкой

Готовит копию документа, пригодную для передачи наружу, и отдельную таблицу
замен, которая остаётся локально. Задача не «убрать фамилии», а сделать так,
чтобы по остатку текста нельзя было восстановить, кто это.

## Инструкции

1. **Три вопроса до начала.** Куда уходит документ (внешняя LLM, MCP, третье
   лицо)? Кто субъекты в документе (физлица, организации)? Что нельзя
   раскрывать по решению пользователя (только ПДн, или ещё коммерческие
   условия и цены)?
2. **Не угадывать политику замены.** Если не сказано — предложить три режима
   (удалить / заменить токеном / обобщить) и работать по выбранному.
3. **Пройти шесть шагов ниже, ничего не пропуская.** Метаданные и колонтитулы
   пропускают чаще всего — именно там утекают имена.
4. **Отдать две вещи:** обезличенную копию и локальную таблицу замен. Таблица
   не уходит наружу никогда.

## Shared guardrails (канон — practice profile)

## Purpose

Отправка документа внешней модели или MCP-коннектору — это передача данных
третьему лицу. Для персональных данных действует отдельный режим
(152-ФЗ: обработка, обезличивание, трансграничная передача), для коммерческой
информации — режим коммерческой тайны (98-ФЗ), для адвокатских материалов —
адвокатская тайна (ст. 8 ФЗ № 63-ФЗ) `[model knowledge — verify]`. Навык
снижает объём передаваемого, но **не решает за юриста**, законна ли передача:
это отдельное решение и, для ПДн, отдельное основание.

## Форма работы

Ограниченная транзакция: один документ, явная цель (куда уходит), явная
резолюция (копия + словарь). Скорость важнее полноты — но остаточный риск
называется всегда, и при трёх и более косвенных признаках работа
останавливается до решения юриста.

## Аудитория и порог делегирования

Юрист или помощник юриста, отправляющий документ наружу. Навык делает замену и
проверку остатков; решение «законна ли передача и достаточно ли обезличено для
конкретного получателя» — за юристом. Низкая уверенность (в документе много
косвенных признаков, метаданные неизвестны) — называется прямо.

## Workflow

### Шаг 1: Инвентаризация прямых идентификаторов

Пройти документ по категориям и выписать найденное в таблицу:

| Категория | Пример | Замена по умолчанию |
|---|---|---|
| ФИО | Иванов Иван Иванович | `СУБЪЕКТ_1` |
| Паспорт, иной документ | серия/номер, кем выдан | `ДОКУМЕНТ_1` |
| ИНН, СНИЛС, ОГРН/ОГРНИП, КПП | 10/12 знаков, 11 знаков, 13/15 | `РЕКВИЗИТ_1` |
| Адрес (жительства, объекта) | город, улица, дом, квартира | `АДРЕС_1` |
| Телефон, e-mail, мессенджер | +7…, user@… | `КОНТАКТ_1` |
| Банковские реквизиты | р/с 20 знаков, БИК 9 | `СЧЕТ_1` |
| Номера дел, договоров, заявок | А40-…, № … | `ДЕЛО_1`, `ДОГОВОР_1` |
| Организация-сторона, должность | ООО «…», генеральный директор | `ОРГ_1`, `ДОЛЖНОСТЬ_1` |
| Транспорт, недвижимость | VIN, госномер, кадастровый номер | `ОБЪЕКТ_1` |

### Шаг 1.5: Падежи, сокращения, инициалы

Имена в документах почти всегда стоят не в именительном падеже, а замена по
одной строке оставляет их в тексте. Для каждого ФИО выписать все формы,
которые реально встречаются в документе:

- падежи: Иванов Иван Иванович / Иванова Ивана Ивановича / Иванову Ивану
  Ивановичу / Ивановым Иваном Ивановичем / об Иванове Иване Ивановиче;
- сокращения: Иванов И. И., И. И. Иванов, Иванов И.И.;
- одна фамилия без имени («директор Иванов»), если она в тексте есть;
- женские формы фамилии, если меняется (Иванова / Ивановой / Иванову).

Практика: собрать формы из самого документа поиском по фамилии без окончания
(«Иванов» найдёт Иванов, Иванова, Ивановой, Иванову), а не придумывать
парадигму по памяти. Затем заменить все найденные формы на один токен.

**Фильтр «ФИО против организации».** Голый регекс из двух слов с заглавных букв
ловит «Банк Санкт-Петербург» и «Мясокомбинат Северо-Запад». Искать ФИО по
триггерам контекста: «в лице», «директор», «генеральный директор»,
«коммерческий директор», «кладовщик», «ИП», «подписал», «действующего на
основании», а также в блоке подписей. Всё, что нашлось без триггера, — на
ручную проверку, а не в замену автоматически.

### Шаг 2: Косвенные идентификаторы

Главная причина утечек — не фамилия, а контекст. Проверить и, если нужно,
огрубить: должность + город + точные даты; уникальные обстоятельства
(«единственный поставщик такого оборудования в регионе», «дело о … с суммой
X»); редкие суммы и нетипичные условия; названия объектов, которые
однозначно указывают на владельца.

Правило: если по трём и более признакам в публичном поиске
находится конкретное лицо или организация — замена **неполная**, и это блокер
для отправки, а не примечание. Отдельно считается связка «населённый пункт +
точный адрес объекта + режим работы/поставки»: её достаточно, чтобы найти
организацию, даже когда названия заменены. Такую связку либо огрубляют
(адрес до района, режим убирают), либо оставляют по явному решению юриста с
записью в Reviewer note.

### Шаг 3: Метаданные, колонтитулы, скрытое

- **DOCX:** свойства файла (автор, последний изменивший, организация,
  комментарий, заголовок), отслеживаемые изменения и примечания, скрытый
  текст, закладки, имена в именах стилей; имя самого файла.
- **PDF:** Author, Creator, Producer, встроенные шрифты-подписи, аннотации.
- **Таблицы:** скрытые листы, фильтры с именами, примечания к ячейкам.
- Практика: пересобрать документ в новый файл (python-docx / soffice) — это
  снимает историю ревизий надёжнее, чем ручная чистка свойств.

### Шаг 4: Токенизация

- Единая схема: `СУБЪЕКТ_n`, `ОРГ_n`, `АДРЕС_n`, `СЧЕТ_n`, `ДЕЛО_n`,
  `СУММА_n` (если суммы закрываются).
- Согласованность: одно лицо — один токен по всему документу, включая
  приложения и подписи.
- Род и число сохраняются («Поставщик обязуется…», а не «они обязуется») —
  иначе модель начнёт догадываться о структуре.
- Таблица замен — отдельный файл `mapping.csv` в локальной папке практики,
  не в каталоге, который синхронизируется или индексируется.

### Шаг 5: Финальный скан остатков

- **Главная проверка — по словарю, а не по регексам:** каждая исходная строка
  из `mapping.csv` (включая все падежные формы из шага 1.5) ищется в
  обезличенном тексте. Хоть одно совпадение — замена неполная.
- Регулярки — второй слой: ИНН 10/12, СНИЛС `\d{3}-\d{3}-\d{3} \d{2}`,
  счёт 20 знаков, БИК 9, телефоны, e-mail, индексы, даты рождения.
- Глазами: шапка, колонтитулы, подписи сторон, приложения, сноски,
  комментарии, свойства файла.
- Отдельно: не осталось ли в тексте прежних названий в сокращениях и
  аббревиатурах (ООО «Р…» превращается в узнаваемое).

### Шаг 6: Реверс ответа

Ответ внешней модели приходит с токенами. Обратная замена — локально, по
`mapping.csv`. Проверить, что модель не «домыслила» токены (не появились
`СУБЪЕКТ_4`, которого не было) и не переставила стороны.

## Формат вывода

```markdown
# Обезличивание: [имя файла]

**Куда уходит:** внешняя LLM / MCP / контрагент
**Дата:** [YYYY-MM-DD]
**Политика:** заменить токенами / удалить / обобщить; суммы [закрыты / открыты]

> **⚠️ Reviewer note**
> - **Заменено:** [N] сущностей, [K] категорий
> - **Косвенные признаки:** [что огрублено]
> - **Метаданные:** [что вычищено: автор, ревизии, комментарии]
> - **Остаточный риск:** [что всё ещё может указать на субъекта]

| Токен | Категория | Вхождений |
|---|---|---|
| СУБЪЕКТ_1 | ФИО | 14 |
| ОРГ_1 | организация | 9 |

## Что отправляется наружу
[путь к обезличенной копии]

## Что остаётся локально
[путь к mapping.csv; в внешний сервис не передаётся]

## Правовая рамка передачи
- ПДн: 152-ФЗ — [обезличено / псевдонимизировано], основание передачи
  определяет юрист `[model knowledge — verify]`
- Коммерческая тайна: 98-ФЗ, режим введён [да / нет / неизвестно]
- Адвокатская тайна: ст. 8 ФЗ № 63-ФЗ — [применимо / нет]
```

## Важное различие (не путать в выводах)

- **Обезличивание** (ст. 3 152-ФЗ) — действия, в результате которых без
  использования дополнительной информации становится невозможно определить
  принадлежность персональных данных конкретному субъекту
  `[model knowledge — verify]`. По этому определению замена на токены с
  отдельно хранящейся таблицей замен — именно обезличивание, **если**
  дополнительная информация действительно отделена от данных и недоступна
  получателю.
- Значит вопрос не в слове, а в факте разделения: если таблица замен лежит в
  том же каталоге, синхронизируется в облако или уходит вместе с обезличенной
  копией — обезличивания нет, данные остаются персональными и передача идёт по
  обычным правилам обработки.
- «Псевдонимизация» — термин западного подхода (GDPR), в 152-ФЗ отдельного
  режима с таким названием нет. В выводах используется конструкция 152-ФЗ;
  западный термин допустим только как пояснение.
- Фраза «обезличено, можно передавать» без указания основания — неверна;
  навык пишет «объём передаваемых ПДн снижен, вопрос основания передачи — за
  юристом».

## Границы с другими навыками

- `CONNECTORS-ru-mcp.md` / `legal-dxe` — решают, куда документ отправляется и
  можно ли это делать; здесь — подготовка документа к отправке.
- `privacy-legal/dpa-review`, `use-case-triage` — правовые основания обработки
  и передачи. Здесь они не проверяются, только называются.
- `commercial-legal/review` — содержательная ревизия договора; при
  обезличивании текст не редактируется.

## Чего этот навык НЕ делает

- Не решает, законна ли трансграничная передача, и не подменяет уведомление
  РКН — это отдельная задача privacy-практики.
- Не гарантирует анонимность: даёт заявленный уровень замены и честный
  остаточный риск.
- Не меняет юридический смысл документа: правки формулировок при обезличивании
  не делаются, только замена и огрубление.
- Не отправляет документ сам: передачу инициирует пользователь, после
  подтверждения (правило `CONNECTORS.md` — write/upload только по явному
  согласию).

## Decision tree

> **Что дальше?**
> 1. **Отправить** — обезличенная копия готова, словарь локально
> 2. **Усилить** — если в документе остались косвенные признаки: огрубить
>    даты, суммы, географию
> 3. **Не отправлять** — если для задачи нужны реальные реквизиты: работать
>    локально (Ollama, локальная модель), а не обезличивать
> 4. **Эскалация** — ПДн клиента или адвокатская тайна: к privacy-практике,
>    навык не выдаёт разрешение на передачу

## Quality checks

- [ ] Политика замены выбрана явно, а не по умолчанию агентом
- [ ] Прямые идентификаторы закрыты по всем категориям
- [ ] Все падежные формы и сокращения имён собраны из документа и заменены
- [ ] Имена искались по контекстным триггерам, а не голым регексом ФИО
- [ ] Скан остатков выполнен по исходным строкам словаря, затем регексами
- [ ] Косвенные признаки проверены (должность + география + даты + уникальность)
- [ ] Метаданные, колонтитулы, комментарии, ревизии вычищены
- [ ] Один субъект = один токен по всему документу, включая приложения
- [ ] Финальный скан остатков выполнен (регулярки + глазами)
- [ ] Таблица замен физически отделена от обезличенной копии (разные каталоги, нет синхронизации)
- [ ] Таблица замен лежит локально и в выводе помечена как не подлежащая передаче
- [ ] Правовая рамка передачи названа, решение о законности оставлено юристу
