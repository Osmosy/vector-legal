# /policy-monitor

**Sweep режим** (без аргумента или `--sweep`):
1. Читать `~/.hermes/legal/privacy-legal/CLAUDE.md` → папка outputs,
   документ политики, дата последнего sweep.
2. Прогнать workflow ниже. Сканировать outputs с даты последнего sweep.
3. Для каждого выхода: извлечь одобренные практики → diff против текущих
   обязательств политики.
4. Классифицировать гэпы: ОБЯЗАТЕЛЬНО (политика искажает практику) vs
   ЖЕЛАТЕЛЬНО (политика молчит).
5. Для каждого гэпа: цитировать политику, описать гэп, драфт правки языка
   + проверить связку с уведомлением ст. 22 (реестр операторов).
6. Обновить дату последнего sweep в профиле.

**Direct query** (с описанием практики):
1. Читать профиль → текущие обязательства политики + сам документ политики.
2. Распарсить предлагаемую практику. Diff против политики: категории ПД,
   цели, третьи лица, сроки уничтожения, права субъектов, раскрытия.
3. Выход: covered / missing / conflicting + предложенный язык для каждого
   гэпа + рекомендация по срокам.

**Расписание:** настроить повторяющееся напоминание в своём планировщике
(календарь, task manager, cron) на еженедельный `policy-monitor`.

```
/privacy-legal:policy-monitor
/privacy-legal:policy-monitor --sweep
/privacy-legal:policy-monitor «Хотим начать использовать геоданные для рассылок»
```

# Монитор дрейфа политики обработки ПД

## Purpose

Политика обработки ПД дрейфует в одну сторону: практика движется вперёд,
политика остаётся за ней. Оценка вреда одобрила новую категорию. Поручение
с новым поручителем подписано (а политика его не знает). Триаж пометил
новый вариант обработки условным с требованием раскрытия, которого в
политике нет. Через полгода кто-то читает политику — и она описывает не то,
что происходит.

По 152-ФЗ это не только hygiene: уведомление РКН (ст. 22) и политика —
публичные обещания, расхождение с которыми — административный риск
(ст. 13.11 КоАП: нарушение порядка сбора/целей) и основание для внепроцессной
проверки. Планируемая встреча с РКН начинается с сопоставления заявленного
и фактического — этот навык держит их в актуальном состоянии, до встречи.

Выход один и тот же: вот гэп, вот предложенный язык.

- `## Политика обработки ПД (обязательства)` — обещания из опубликованной

Если `## Выходные документы` содержит `[PLACEHOLDER]`:

Читать сам документ политики по пути из `## Выходные документы` →

документ авторитетен для правок языка.

## Обязательства живут на нескольких поверхностях — sweep все

Сайт-политика — одна поверхность. Программа ПД делает обязательства минимум
в пяти местах, которые РКН (и суд) сопоставляют между собой:

1. **Сайт-политика обработки ПД** — публичный документ.
2. **Уведомление РКН (ст. 22) / Единый реестр операторов** — заявленные цели,
   категории, субъекты, сроки. Расхождение политики и заявленного — прямая
   находка при проверке.
3. **Поверхности согласий в продукте** — чекбоксы, формы, оферты, ЛНА для
   сотрудников. Согласие собирается под конкретную цель (ст. 9); если
   обработка расширилась, согласие не покрывает новую цель.
4. **Согласия по биометрии (ст. 11 — письменная форма)** — если в практике
   появляется биометрия, а согласия в форме «чекбокс» — системный дефект.
5. **Поручения поручителям (ч. 3 ст. 6)** — перечень целей/действий в
   подписанных поручениях должен соответствовать перечню целей политики.

**Добавить в профиль поля location/last-updated для каждой поверхности.**
Sweep сверяет каждую с текущей политикой и флагает расхождение:
«Политика обновлена [дата]. Реестр операторов — не обновлялся с [более
ранней даты] — может не покрывать новую категорию. Согласия на сайте
последний раз правились [дата] — сверить цели.»

Компания с чистой политикой и неперезаписанным уведомлением РКН — компания
с находкой на первой же проверке. Sweep поверхностей, не только документа.

## Mode 1: Sweep

### Определить скоуп

Читать `## Выходные документы` → **Last policy sweep**. Сканировать output
файлы dated после этой даты. Если даты нет — сканировать всё и сказать:
«Первый sweep — сканирую все outputs».

Пустая папка или нет новых файлов:

> «Новых выходов с [дата]. Политика выглядит актуальной. Следующий
> scheduled sweep: [дата].»

Обновить **Last policy sweep** в профиле на сегодня после завершения.

### Что читать в каждом типе выхода

**Оценки вреда (pia-generation):**
- Извлечь: категории ПД, цели, поручители, сроки уничтожения, права
  субъектов, условия запуска
- Флагать: всё из списка, чего нет в текущих обязательствах политики

**Ревизии поручений (dpa-review, подписанные/согласованные):**
- Извлечь: поручители добавлены, места обработки согласованы, цели
  покрыты, обязательства перед субъектами созданы терминами поручения
- Флаг: поручители, не названные в политике (если она называет), новые
  категории обработки, новые места/страны, обязательства, несовместимые
  с политикой

**Триажи (use-case-triage, ОЦЕНКА/PROCEED):**
- Извлечь: что одобрено, какие условия наложены, предполагают ли они
  публичное обязательство (напр. «раскрытие до запуска»)
- Флаг: одобренные практики, не покрытые политикой, условия, требующие
  языка политики

**Ответы субъектам (dsar-response):**
- Извлечь: новые категории ПД, которых не было в прошлых ответах, новые
  системы в списке
- Флаг: категории, собираемые, но не названные в политике

### Идентификация гэпов

Для каждого флага — оценить:

**ОБЯЗАТЕЛЬНОЕ обновление** — политика обязывается так, что выход
противоречит, или обработка идёт, а политика молчит. Не-обновление —
существенное искажение.

> Пример: Политика говорит «мы собираем ФИО, email, телефон». Оценка
> одобрила сбор геолокации. Политика о гео молчит — сбор без раскрытия.
> ОБЯЗАТЕЛЬНО: обновить политику и проверить уведомление РКН (цель
> «геоаналитика» там заявлена?), при необходимости — свежие согласия (ст. 9).

> Пример 2: Политика обещает уничтожение «в течение 30 дней после
> отзыва согласия». Ответ субъекту обещал 60 дней — потому что бэкапы.
> ОБЯЗАТЕЛЬНО: либо привести практику к 30 дням, либо честно описать
> исключение (бэкапы) в политике.

**ЖЕЛАТЕЛЬНОЕ обновление** — политика молчит, не противоречит. Практика
защитима без обновления, но чище — с ним.

> Пример: Политика говорит «мы можем передать данные подрядчикам». Поручение
> подписано с новым подрядчиком. Политика его не называет и не запрещает.
> ЖЕЛАТЕЛЬНО: обновить актуальный список поручителей, если ведётся.

## Mode 2: Direct query

### Распарсить предлагаемую практику

Из описания пользователя — идентифицировать: категории ПД, цели, новых
третьих лиц/поручителей, сроки хранения, новые раскрытия, влияние на
права субъектов.

### Diff против политики

| Параметр | В политике | В практике | Статус |
|---|---|---|---|
| Категории ПД | | | covered / missing / conflicting |
| Цели | | | |
| Третьи лица / поручители | | | |
| Сроки хранения/уничтожения | | | |
| Права субъектов | | | |
| Локализация/трансграничка | | | |

### Формат выхода

```markdown
[HEADER]

# Policy Monitor — правка: [практика]

**Вывод:** покрытие политики: 🟢 достаточно / 🟡 гэп, но защитимо /
🔴 конфликт — правка обязательна до запуска

## Гэпы
[по каждому: цитата политики, гэп, предложенный текст]

## Связанные действия
[уведомление РКН (ст. 22), согласия, поручения, срок]

## Рекомендация по срокам
[править до запуска / при следующей версии политики]
```

Direct-запрос — тоже проверка в реестре операторов: если предлагаемая
практика вносит новую цель обработки, уведомление РКН (ст. 22) может
требоваться обновить раньше правки политики `[verify]`.

---

## Что этот навык не делает

- **Не правит политики без подтверждения.** Все правки — драфты; заливка —
  после апрува юриста.
- **Не переписывает политику с нуля** — для этого политика-документ и
  профиль; навык предлагает точечные правки против найденных гэпов.
- **Не подаёт обновления уведомления РКН** — готовит черновик и флагает
  необходимость; подача — ответственный.
- **Не обрабатывает изменения закона** — это `reg-gap-analysis`
  (входящее изменение → гэплан). policy-monitor — внутренний дрейф:
  практика → политика.
