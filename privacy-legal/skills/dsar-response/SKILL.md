3. Классифицировать тип запроса. Проверить триггеры эскалации — если

именах файлов.

# Ответ на запрос субъекта ПД

## Matter context

Проверить `## Matter workspaces` в practice profile. Если `Enabled: ✗`
(дефолт in-house) — работать на practice-level. Если включено — спросить,
для какого дела. Выходы в
`~/.hermes/legal/privacy-legal/matters/<slug>/`. Чужие дела не читать без
`Cross-matter context: on`.

---

## Destination check

Ответ субъекту — **внешний deliverable**: header work product на письмо НЕ
вешается. Внутренние анализы отказов, журналы и memo идут с header по
профилю и хранятся отдельно. Канонический текст — practice profile →
Shared guardrails → Destination check.

## Purpose

У запроса субъекта есть срок (30 дней по 152-ФЗ), процесс (верифицировать,
найти, оценить отказы, ответить) и много мест, где всё ломается. Навык
проводит по шагам и готовит черновик ответа. Всё — черновик для юриста;
отправка — решение человека.

## Jurisdiction assumption

Анализ применяет 152-ФЗ. Если субъект — EU-гражданин и применим GDPR
(экспортные клиенты) — параллельно применить ст. 15–17 GDPR: сроки и
основания отказов другие (1 месяц + продление 2 месяца; Art. 12(4)–23).
Боковая колонка, не замена 152-ФЗ (см. profile → Jurisdiction recognition).

## Загрузить процесс

Прочитать `~/.hermes/legal/privacy-legal/CLAUDE.md` →
`## Процесс запросов субъектов`. Там:

- Список систем (все места, где живут ПД)
- Метод верификации
- SLA (внутренний; закон — 30 дней, см. ниже)
- Кто обрабатывает рутину, кого эскалировать

Если список систем пуст — флаг: полный DSAR без знания, где искать, невыполним.

## Workflow

### Шаг 1: Классифицировать запрос

Определить, какое право субъект реализует:

| Право | Норма 152-ФЗ | Суть |
|---|---|---|
| Сведения об обработке (доступ) | ст. 14 | Оператор обязан сообщить: подтверждаются ли факты обработки, цели, способы, категории ПД, сроки, источники, перечень действий, передача третьим лицам, состояние обработки |
| Уточнение / блокирование / уничтожение, если данные неполны, устарели, неточны или получены незаконно | ст. 20 ч. 1 | Требование уточнить, заблокировать или уничтожить |
| Уничтожение при отозванном согласии | ст. 21 ч. 1 | Отзыв согласия → уничтожение в 30 дней, если нет иного основания (ст. 6 ч. 2 — обработка без согласия по договору/закону продолжается законно) |
| Уничтожение при незаконной обработке | ст. 21 ч. 2 | Устранить нарушение в 3 рабочих дня |
| Отзыв согласия | ст. 9 ч. 2 | Согласие отзывается в любой момент |
| Прекратить обработку/уничтожить, если цели достигнуты | ст. 21 | Проверить цели |

Сроки: **30 дней** с даты обращения для ответов по ст. 14 (через оператора),
20 и 21 (ч. 2 ст. 20; ч. 2 ст. 21). Комбинированные запросы («удалите
аккаунт и пришлите мои данные») — обрабатывать как связанные: два требования,
один таймлайн.

**Осторожно: это черновик правовой позиции — исследовать актуальную редакцию
152-ФЗ перед опорой на номер статьи или срок.** Поправки 2023+ меняли
формулировки. Каждый номер статьи тегировать `[model knowledge — verify]`,
если не проверено против первоисточника в этой сессии.

### Шаг 2: Верифицировать личность

По методу из профиля. Подходы:

- **Авторизованная сессия:** запрос из-под учётной записи → личность
  подтверждена
- **Совпадение канала:** запрос с контакта, который есть на файле →
  обычно достаточно для низкорисковых запросов
- **Усиленная верификация:** высокие суммы/удаление учётки → контрольный
  вопрос, телефон, документ

**Калибровать к риску.** Сверхверификация превращает процесс в барьер
(претензия субъекта, проверка РКН). Недоверификация — отдать чужие ПД
мошеннику.

Если личность не верифицирована — черновик:

> Мы не можем убедиться, что запрос исходит от субъекта, чьи данные
> затронуты. Для продолжения: [шаг верификации]. Не подтверждаем наличие
> или отсутствие ПД до идентификации.

Не тянуть: ответ с просьбой верификации в первые дни, не на 29-й день.
Таймлайн не останавливается молчанием — фиксировать в журнале каждую дату.

### Шаг 3: Найти данные

Обходить список систем из профиля. Для каждой:

| Система | Запрос отправлен? | ПД найдены? | Что |
|---|---|---|---|
| Прод-БД | | | |
| HR-система / 1С:ЗУП | | | |
| CRM / продажи | | | |
| Поддержка (тикеты, почта) | | | |
| Логи / видеонаблюдение / СКУД | | | |
| Бэкапы | | | (обычно оговорка — см. отказы) |
| Поручители (подрядчики) | | | (направить требование уничтожения/сообщения; ответственность перед субъектом остаётся на операторе) |
| Аналитика/трекинг | | | |

**Если мы поручитель:** «субъект» обычно — конечный клиент нашего оператора.
Проверить, не наш ли это запрос в обработку: поручитель обязан сообщить
оператору о запросе и не отвечать субъекту напрямую без поручения. Многие
поручения содержат правило «переадресовывать запросы оператору».

### Шаг 4: Анализ отказов

Не всё подлежит выдаче или уничтожению. **Исследовать нормы перед тем, как
предложить отказ.** Для каждого элемента — все основания отказа, которые
реально применимы:

| Основание | Норма | Суть |
|---|---|---|
| Обработка необходима для исполнения договора, сторона которого субъект | ч. 2 ст. 6 (п. 5) | Отзыв согласия не уничтожает данные, нужные по договору: расчёты, бухгалтерия |
| Обработка по закону (налоговые, кадровый учёт, бухгалтерия) | ч. 1 ст. 6 (п. 2, 3), ФЗ о бухучёте, НК | Сроки хранения установлены законом — уничтожение до истечения незаконно |
| Обработка для правосудия/исполнения судебного акта | п. 3, 8 ч. 1 ст. 6 | Хранение в связи с судебным спором |
| Защита жизненно важных интересов | п. 4 ч. 1 ст. 6 | Узкий случай |
| Статистические/исследовательские цели с обезличенными данными | ст. 6 ч. 1 п. 9–10, ст. 20.2 | Если не затрагивает права субъекта |
| Обезличенные данные | ст. 20.2 | Обезличенные не «данные субъекта» для целей ст. 21 |

**Не сужать список отказов на субъективном решении.** Навык предлагает
отказы там, где есть добросовестное основание, и тегирует спорные; юрист
сужает список до отправки. Отказ, который потом окажется необоснованным —
дорого; лишняя кандидатура на отказ исправляется юристом за секунду. Предпочитать
исправимую ошибку (recoverable error).

Каждый предлагаемый отказ — с явной пометкой: **«предложено — требует
проверки юристом. Отказ субъекту отправляется с обоснованием по норме —
необоснованный отказ становится предметом жалобы в РКН (ст. 13.11 КоАП для
нарушений) или суда (ст. 24 152-ФЗ).»**

Повторяющиеся вопросы:

- Содержит ли запись ПД других людей? → редактировать перед выдачей
- Есть ли законный срок хранения, блокирующий уничтожение? → процитировать
- Судебный спор по этому субъекту? → litigation hold
- Бэкапы? → ротация бэкапов — документируемое ограничение, не общий отказ;
  при восстановлении из бэкапа данные субъекта подлежат обработке по тем же
  правилам (бэкап — не основание отказа сам по себе)
- Данные о трудовой деятельности → сроки из ТК/архивных правил

**Каждый отказ документировать.** Если РКН спросит, почему не уничтожили —
ответ «по закону о бухучёте» должен иметь цитату и срок.

### Шаг 5: Готовить ответ — ДВА ПИСЬМА

> **Pre-flight источников.** Перед выпуском писем или анализа отказов —
> проверить доступность web search. Записать в Sources: строку Reviewer
> note внутреннего анализа (не внешних писем): «не подключено — из модельных
> знаний; отказы, сроки и основания — самые fabrication-prone места,
> проверять до отправки любого отказа». Per-citation теги остаются inline.

Большинству субъектов (и РКН при проверке) ожидаемо **быстрое
подтверждение получения**, отдельное от содержательного ответа. Два письма,
не одно.

- **5а — Подтверждение получения.** В течение дней с получения (цель:
  тот же день — 3 дня, всегда внутри 30-дневного окна). Подтверждает
  получение, фиксирует, что оператор понимает под запросом, срок ответа,
  запрашивает верификацию, если не завершена. НЕ содержит содержание
  ответа. Своевременное подтверждение — первый видимый регулятору сигнал
  работающего процесса.
- **5б — Содержательный ответ.** Само сообщение (сведения по ст. 14 /
  уточнение / уничтожение) или мотивированный отказ. К 30-дневному сроку
  (или внутреннему SLA, если короче). Только после верификации и Шага 3/4.

**Clock-start rule.** 30-дневный срок идёт с даты обращения, не с момента
завершения верификации. Не останавливать срок молча.

#### 5а — Шаблон письма-подтверждения

```markdown
Тема: Ваш запрос о персональных данных получен — [Компания] — [дата]

Уважаемый (-ая) [Имя],

Мы получили ваш запрос от [дата] о [сведениях об обработке / уточнении /
уничтожении / отзыве согласия].

**Как мы понимаем ваш запрос:** [одно предложение перефраза]

**Что дальше:**
- Ответ мы подготовим до [дата — не позднее 30 дней с даты обращения по
  152-ФЗ; внутренний SLA, если короче].
- [Если нужна верификация:] Для защиты ваших данных просим [шаг
  верификации] — ответ работаем готовить параллельно.
- Отвечаем по каналам, указанным вами, либо заказным письмом.

Если у вас вопросы — [контакт ответственного за организацию обработки
(ч. 1 ст. 22.1)].

[Подписант]
```

#### 5б — Шаблоны содержательных ответов

**Сведения об обработке (ст. 14):**

```markdown
Тема: Ответ на ваш запрос о персональных данных — [Компания] — [дата]

Ваш запрос от [дата] рассмотрен. Сообщаем:

1. **Обработка подтверждается:** [да/нет]
2. **Правовое основание обработки:** [соответствующий пункт ч. 1 ст. 6
   152-ФЗ + ссылка на договор/согласие]
3. **Цели обработки:** [из перечня целей/политики]
4. **Применяемые способы обработки:** [сбор, запись, систематизация,
   накопление, хранение, уточнение, использование, передача (обезличивание),
   блокирование, удаление, уничтожение — фактические]
5. **Категории ПД:** [перечень по факту обработки]
6. **Сроки обработки и хранения:** [сроки, включая сроки уничтожения]
7. **Порядок осуществления прав и способы обращения:** [ст. 14 ч. 7]
8. **Сведения о передаче третьим лицам:** [подрядчики-поручители, категории]
9. **Состояние обработки на дату ответа:** [активна / прекращена /
   заблокирована]
10. **Сведения о трансграничной передаче** (если есть): [страны — сверить
    с перечнем приказа РКН №931 `[verify]`]
11. Наименование/ФИО и адрес оператора, контактные данные ответственного
    за организацию обработки [ч. 7 ст. 14 152-ФЗ — полный перечень
    обязательных сведений проверять по актуальной редакции]

**Чего мы не включили и почему:**
- [Категория] — [основание по норме, процитированное]

**Право на обжалование:** Вы вправе обжаловать наши действия в
Роскомнадзор или в суд (ст. 24 152-ФЗ).

[Подписант]
```

**Уничтожение (ст. 21):**

```markdown
Тема: Ответ на ваш запрос об уничтожении персональных данных — [Компания] — [дата]

1. [Уничтожено: перечень категорий, дата, способ — «уничтожение» по ст. 13
   приказа ФСТЭК №21 `[verify — способ фактического уничтожения по
   актуальным требованиям]`]
2. [Не уничтожено, почему — норма + срок хранения, с цитатой]
3. [Поручители уведомлены о требовании уничтожения — даты]
4. Подтверждение поручителям о уничтожении — [статус/срок]

Право на обжалование — Роскомнадзор/суд (ст. 24).
```

**Отказ (с обоснованием):**

```markdown
Тема: Ответ на ваш запрос — [Компания] — [дата]

Ваш запрос от [дата] рассмотрен. Сообщаем об отказе в [действии] в части:

- [что именно] — отказ на основании: [конкретная норма 152-ФЗ / ФЗ / срок
  хранения по НПА], поскольку [фактическое основание].

В остальной части: [что сделали — срок, подтверждение].

Порядок обжалования: Роскомнадзор ([адрес/сайт]), суд (ст. 24 152-ФЗ —
компенсация морального вреда).

[Подписант]
```

**Отказ, который не может отправляться без проверки юристом:** любой мотив,
который сформулирован общо («техническая невозможность», «коммерческий
интерес»). Общие мотивы РКН расценивает как необоснованные — либо норма с
цитатой, либо выполняем.

### Шаг 6: Запись в журнал запросов

Каждый запрос, каждый ответ, каждый срок — в журнал (из профиля). Формат
записи:

```markdown
[YYYY-MM-DD] [тип запроса: ст.14 / ст.20 / ст.21 / согласие] [верификация:
метод/статус] → [решение: выдано N систем / уничтожено X / отказ (норма)] →
[ответ отправлен YYYY-MM-DD] → [исполнители]
```

Журнал — главный артефакт при проверке РКН: он доказывает, что 30-дневный
срок соблюдён, отказы обоснованы, поручители уведомлены.

## Шлюз: отправка письма

**Перед тем как идти отправлять письмо субъекту:** читать
`## Кто использует` профиля. Если Роль = не-юрист:

> Отправка ответа субъекту имеет правовые последствия: содержание, отказы и
> умолчания проверяемы РКН и судом; неверный отказ — административный риск
> (ст. 13.11 КоАП) и компенсация морального вреда (ст. 24 152-ФЗ).
> Согласовал с юристом? Если нет — бриф: субъект, что запрошено, что найдено
> по системам, что отказывается и на какой норме, верификация, срок, три
> вопроса юристу.

Не идти за шлюз без явного yes. **Ничего не отправлять автоматически.**

## Reviewer note (внутренний)

На внутренний анализ (Шаг 4, решение по системам) — Reviewer note по
профилю. На внешние письма — НЕТ.

## Финал: decision tree «Что дальше?»

Завершить decision tree по профилю (подготовить ответ / направить
требования поручителям / эскалация / добавить запись в журнал / наблюдать).

## What this skill does not do

- **Не решает, законен ли сам запрос субъекта.** Отказ — всегда за юристом.
- **Не заменяет журнал.** Навык готовит запись, не ведёт журнал.
- **Не выполняет уничтожение в системах.** Навык готовит требования и
  подтверждения; фактическое уничтожение — ИТ/подрядчики.
- **Не подаёт жалобу/ответ на жалобу от имени компании.** Только черновики.
